## 4. 材料策略：让玻璃出现在有意义的地方

### 4.1 场景分配

| 场景 | 本次方向 | 可读性与布局要求 |
| --- | --- | --- |
| 沉浸计时操作带 | 保留现有可调功能玻璃 | 原有大小、直边贴屏形状、计时器居中及 0–100% 非线性材料映射不变；滑杆仍只控制此处 |
| 世界 HUD、坐标／重置控件、建筑记忆、世界瞬时提示 | 积极复用固定高可读性玻璃 | 世界内容确实透过材料；深色调建立可靠文字对比，不随背景丢失状态 |
| 位于实际内容上方的选择菜单、调整 Sheet、非破坏性弹出摘要 | 优先评估并采用液态玻璃 | 保留来源、遮罩、滚动、焦点和返回关系；不能透得让前后两层文字混读 |
| 设置分组及蓝图库／资源包／备份外层面板 | 保留轻玻璃分组 | 延续卡外标题、分组卡和明确选中态，降低过重的白色覆盖与悬浮投影；长数据内容可以使用实底内层 |
| 任务正文卡、统计图表与热力图、输入字段 | 高可读性实底为基准，按真实效果判断是否有局部玻璃收益 | 不强制把整页全部玻璃化；图表配色、输入边界与编辑状态优先 |
| 导入替换、删除、结束专注等关键决策区 | 操作和文字区域维持稳定高对比底面 | 外层若采用玻璃，不能削弱危险动作、禁用状态或正文可读性 |
| 顶栏与主导航 | 本阶段保持现有结构和实底材料，统一控件与 token | 不新增浮岛导航、改变导航可达性或缩小世界面积 |

对每个新增玻璃位置，在结果报告中写一句：它透出的是什么、帮助表达什么层级、低性能／减少透明度时如何回退。静态背景下收益很小的材料允许更轻，不添加装饰背景或常驻动画来“证明玻璃存在”。

### 4.2 材料实现契约

- 采用明确的语义材料类别：内容实底、设置轻玻璃、世界固定玻璃、沉浸可调玻璃。可以共享底层 token 与工具类，但参数不能串到不相关场景。
- 玻璃表现由色调透明度、背景扩散、克制的饱和／亮度、表面反光和软投影共同组成；无需追求物理精确折射。优先沿用现有 CSS，不引入新的 Shader、Canvas 采样循环或第三方玻璃库。
- 不使用硬亮边、重复 inset 高光或多层阴影制造“叠片”。沉浸操作带尤其保持已验收的向世界侧扩散软阴影。
- 圆角与材料分开定义。设置分组可保留 18px 圆角；其他组件按语义半径统一。计时页当前小任务卡与沉浸带保留直边特例，不能因为玻璃而改变它们的几何形状。
- 浅／深主题均定义完整材料与交互状态。正文至少 4.5:1，大字至少 3:1；复杂世界背景取多个亮暗样本实际复核，不只检查 token 静态色值。
- `prefers-reduced-transparency` 命中时所有适用表面回退实底且停止 backdrop filter；不支持 backdrop filter 的浏览器同样能读清内容。回退必须在最终 CSS 级联后仍生效。
- 不把减少动态效果等同于减少透明度；两者分别处理。前者停止非必要动效，后者改变材料。
- 新玻璃不增加世界重建、不启动隐藏页面的持续动画。滚动和控件反馈不能等待玻璃动画结束；只为展示引入的性能成本必须可测量、可回退。

## 5. UI 工作项

### UI-27-01：收敛设置页初稿

保留已经实现的分组列表、分段控件、iOS 风格开关、“高级”中的坐标开关和原有设置功能。落实上面的轻玻璃方向，并修复以下已知问题：

1. 360px 预览中星期按钮实际约 37×44px。所有独立触控命中区域应至少 44×44 CSS px；空间不足时换行或采用能满足尺寸的排布，不把七个按钮压窄。视觉旋钮可小于 44px，但其关联 label 的真实命中区要足够且互不覆盖。
2. `settings.css` 前部的减少透明度回退，被后面三个数据面板的同优先级材料声明覆盖。检查最终计算样式，不只移动一条规则后假定修复。
3. `settings-layout.spec.ts` 只检查按钮高度。补充宽度、相邻命中区域不重叠和键盘焦点；允许断点重排，不固化“七枚必须同排”的旧假设。
4. 数值输入可清空再输入，失焦／确认后依既有规则收敛；开关与数值不能互相挤压。深色和禁用状态保持清楚。
5. 毛玻璃滑杆保留 0／50／100 的显著差异、5% 步进与持久化；按住或拖动时没有系统蓝框、轨道变色或点击高亮。键盘焦点必须可见。

### UI-27-05：共用组件与 CSS 所有权

- 盘点并统一主按钮、次级文字按钮、图标按钮、开关、分段选择、数字输入、选择菜单、Sheet／对话框展示壳、提示与材料表面。优先提取已有两个以上实际消费者的重复结构；避免搭建没有消费方的通用框架。
- 统一字号层级、语义颜色、间距、半径、焦点、按下、禁用、错误和短动效。为合理例外显式命名，不靠选择器碰巧命中。
- 输入沿用 `NativeImeTextEntry` 等既有安全边界；不要把中文草稿改回每次渲染强制回写的受控输入。
- 按组件迁移 `foundation.css` 和 `theme.css` 中的旧规则；迁移一块，核对引用并删除被取代的那一块。新组件直接用 token，使深色主题通过变量生效。不要追加 `v27-overrides.css` 或增加全局 `!important` 补丁。
- `styles/index.css` 的导入顺序与所有主题／减少透明度覆盖一起检查。动效不改变布局，默认短促、可中断，减少动态效果下保留状态信息。

### UI-27-06：按用户流程统一页面

| 页面／状态 | 本轮重点 | 必须保留 |

| 空闲计时工作台 | 任务标题、当前小任务、轮次调整与主按钮的层级 | 小任务卡直边、主操作首屏可达、计划宿主来源 |
| 沉浸专注与休息 | 玻璃、长任务名、结束按钮、阶段信息 | 原几何、计时器居中、专注与休息操作区别 |

“统一”以同类操作一致为目标，不给所有页面套同一个盒子，不新增今日下一步或其他产品流程。对 `App.tsx` 内部 UI 按第 3 节交付待接线部分。

### UI-27-07：视觉资产规范与清单

## 6. 验证范围与停止条件

### 6.1 每块改动完成后

- 运行 Web 类型检查；修改有实质行为的控件时，验证其键盘、草稿提交、取消与可访问语义。纯间距／颜色不需要新写镜像实现的单元测试。
- 在实际应用中走受影响路径，保留有业务价值的断言。模拟数据使用合成 fixture，不把用户备份、第三方资源包或真机私有内容提交进仓库。
- 定向 E2E 参考：设置用 `settings-layout.spec.ts`、`v23-appearance.spec.ts`、`world-coordinate-setting.spec.ts`；共享布局用 `responsive-qa.spec.ts`、`focus-regressions.spec.ts`；计划／汇报涉及 `v21-marathon.spec.ts`、`v22-marathon-lane.spec.ts`、`v24-marathon-settle.spec.ts`；退出／结束展示涉及 `v22-integrity-ended.spec.ts`。按实际改动选择，先核对当前测试标题和平台限制。
- 命令从自己的仓库根运行，例如 `npm run typecheck -w @tomato-clock/web`、`npm run test:e2e -w @tomato-clock/web -- tests/settings-layout.spec.ts --project=mobile-chromium --workers=1`。依赖多个 WebGL 场景的验证串行运行。

### 6.2 视觉与状态矩阵

- 视口：360×800、412×915、915×412、768×1024、1440×900。主要改动页面在浅／深两种主题截图；相同状态、数据、世界种子和时间用于前后对照。截图必须来自实际实现，不以生成图或孤立 mockup 替代。
- 检查默认、选中、按下、键盘焦点、禁用、空、长中文／英文、200% 字号、安全区与软键盘。按钮长文案不靠截断解决，容器不出现意外横向溢出。
- 所有适用玻璃检查普通、减少透明度与 backdrop filter 不可用路径；所有动效检查减少动态效果。测试工具不能模拟某能力时记录限制并交给集成／真机阶段，不降低标准或伪造通过。
- 新增玻璃叠在世界上时，至少检查明亮地形与夜间场景；普通文本、危险按钮和计时均清晰。玻璃容器不能裁切菜单／焦点环，弹层不能被世界 overflow 遮住。
- 全局 CSS／公共控件完成后补核心 Web smoke 和相应稳定 UI 回归。开关、主题、滑杆、记忆面板的展示改变不应增加世界重建；记录计数、错误日志以及短滚动／交互观察，不宣称浏览器结果代表手机 GPU 性能。

### 6.3 交付阶段边界

本 UI 任务止于定向测试和审计材料。不要启动全量发布准备、构建 APK、安装 OnePlus、改版本、打 tag、推送或发布。跨域风险超出本交接时列入集成检查。集成负责人随后安排两阶段 APK 流程：验证版按改动测试，正式候选按冻结源码完整门禁。

5. 实际执行的命令、进程退出码、通过／失败／跳过、耗时、报告路径与对应源码指纹；不要只提供滚动日志里的测试计数。
6. 五视口、浅深主题、输入法、触控、焦点、减少动态／透明度矩阵，明确未测项目。
7. 需要核心 agent 接线的最小接口说明：值由谁提供、回调返回什么、取消／失败如何显示；不得携带第二份计时或计划真相。
8. 原本存在但未修复的行为问题与新增风险，尤其是“计数正确但离开提示不弹”。UI 演示能显示该提示不等于真实生命周期已修复。

最终把这份报告与实现交给用户；由用户交回核心 agent 审计后决定集成和上机。
