# blockcolc 验证与交付

按实际影响选择验证；小改动不逐级跑遍所有层级。命令定义以各 `package.json` 和现有工具为准。

## 选择入口

| 改动 | 验证 |
| --- | --- |
| 文档、skill | 引用、结构、规则一致性；不构建应用 |
| 单一业务/交互/渲染行为 | 受影响纯测试、原生测试或实际浏览器 spec；必要类型检查 |
| 多模块集成 | `npm run test:fast`；主要用户路径受影响时补 `npm run test:web:smoke` |
| 共享计时、恢复、存储或渲染契约 | 受影响稳定回归：`npm run test:e2e -w @blockcolc/web`；按传播范围扩大 |
| 正式版本输入冻结 | 完整门禁；常规入口 `tools/Prepare-Release.ps1` |
| runner、fixture、构建或发布工具 | 对应工具反例检查及受影响的上层验证，不默认重跑应用全量 |

定点示例：`npm run test:e2e -w @blockcolc/web -- tests/resource-pack.spec.ts --project=mobile-chromium --workers=1`。
扩展/诊断按需运行：`npm run test:extended`、`npm run test:web:diagnostics`、`npm run test:diagnostics -w @blockcolc/voxel`。
`npm run test:web:release` 使用优化 test-mode 构建，分 core/visual/renderer，renderer 单 worker；正式 APK 不含测试探针。

## 用什么证明修好

从原始操作建立反例，能复现时确认旧实现确实失败。保留必要的模式、数据量、输入与环境条件，同时检查失败和恢复方向。

- 输入/UI：实际进入、操作、退出与返回；受影响主题、长文本、IME、字号和安全区。手势检查双向、取消及滚动/双击竞争，不用直接调用处理函数代替真实输入。
- 世界/资源：固定必要时间和随机条件，等有效帧后审看主体、阴影、材质、轮廓；主世界与小预览分别检查。导入沿文件/解析/校验/保存/恢复/实际采用验证，不只调大常量。视觉检查按 DESIGN 和专属 skill 的清单执行。
- 计时/统计/存储：模式归属、时长与轮次守恒、跨日、中断、旧数据、重复恢复和写入失败。
- 外部服务/原生：检查传输、真实响应、解码、桥接、UI 和回退；服务控制台成功不代表应用有效。设备恢复见 `docs/ANDROID-RECOVERY-MATRIX.md`，性能入口为 `tools/Measure-AndroidStartup.ps1`；浏览器不代签 OEM 结果。
- 性能：同机同数据比较操作到反馈，定位保存、重建和帧成本；结构更清晰不等于更快。

产品决定改变才修改旧预期；改过的断言必须重新执行，不以放宽阈值换绿色。临时 probe 与正式回归分开，历史版本名不是删除有效测试的理由。

## 完成、失败与复用

- 每次必要验证记录命令、输入指纹、最终退出码、原始报告及失败/跳过/重试；小定点不要求额外建立一套证据系统。
- 源码、端口、dist 和输出目录保持单一写入者。长任务等完成事件，不按分钟检查进度；提前失败或需要输入时处理。
- 超时、中断、缺最终结果不能记通过；skipped/flaky 分开记录原因和交付影响。截图存在、画布非空和编译成功都不能独自代表行为验收。
- 失败先区分产品、测试和环境原因。单例重跑用于诊断，不能拼成完整门禁。
- 原应用门禁通过、仅构建/交付工具失败时，先审查应用源码、依赖、配置和生成资产差异，只补受影响工具与构建验证。保留原报告，核对最终包内资产；不从头重跑未受影响全量，也不冒称新一轮 Prepare 完成。
- 应用行为或测试输入改变时重验其影响范围；正式候选是否需要新的全量由冻结输入及传播风险决定。不能把不同输入的局部结果拼成一个完整通过，也不能沿用已改变应用内容的用户确认。

原始报告由索引关联，摘要和计数由工具生成，不手抄多份长期维护。日志使用合成数据，不输出凭据、任务正文或完整服务响应；保全与归档见 `docs/WORKSPACE-MAINTENANCE.md`。

## 测试包：同轮成对，交付分离

1. 完成本轮验证后冻结应用源码、依赖、配置和资产。每个新交付轮递增 versionCode，高于任一通道已交付/发布轮；日常编辑不递增，同摘要重复交付不算新轮。
2. 顺序构建标准与含好友服务器模块的私有 APK：标准用 `tools/Build-Verification-Apk.ps1 -ArtifactOnly -DeliveryRoundId <本轮ID>`；私有用私有工作区 `tools/Build-IntegratedVerification.ps1 -RepositoryRoot <主工作树> -DeliveryRoundId <同一ID>`。尖括号是待替换参数，不是可原样执行的命令。
3. 两包使用同一冻结应用输入、版本、包名、签名和非空 DeliveryRoundId，分别记录通道与 SHA-256；标准最终产物必须不含私有实现/config。另一通道同 code 的交付由既有版本预检校验，不能仅凭人工声明“同一轮”。
4. 私人包默认只留本地。安装、上传测试仓库与服务部署各按当次授权；测试仓库仅传授权 APK，保留旧包。复制、上传、回读或安装时实际比较摘要。
5. 获准安装时覆盖升级，不清数据；手机忙就暂停，只有明确允许才用 `-AllowBusyDevice`。核对安装身份和设备包摘要后交用户体验，不默认继续手机 UI 巡检。

本地补充蓝图直接消费工作区 `packages/voxel/src/local-blueprints/`。日常构建不扫描外部素材目录；仅新增/更新资产时显式运行 `npm run package:local-builtins -w @blockcolc/litematic -- <输入目录>`，检查稳定 ID、类别和摘要，未提供合法输入就失败。不删除原件，不猜新增蓝图类别；两通道共用同一份资产。

## 发布：接受精确产物，不重复体验

发布必须有当前用户授权。项目已批准的优先路径是：完整冻结门禁 → 同轮标准/私人包 → 用户体验私人包并明确接受 → 发布对应标准候选。不能提前代签，也不再要求第二次标准包体验、重复全量或重建已接受的候选。

保留传统 Prepare → Install → Accept → Publish，供用户要求精确标准包设备验收时使用；它不是成对验收路径的强制附加步骤。工具只支持哪条路径就如实记录，不捏造 installation 或 phase 来绕过检查。

发布前绑定原报告、两包核心/源码/配置关系、精确标准候选摘要和用户确认。验证 APK 不得直接改名冒充正式候选；正式候选须有独立来源和构建证据。应用内容改变则重新验证并取得对新内容的确认；仅修构建工具按前述范围规则续跑。

核对被发布提交的 CI、tag、Release/Latest、唯一授权标准资产及实际下载摘要/包身份/私有隔离。网络命令失败先查远端是否已成功，不盲目重复发布或覆盖资产。新设备安装不是已经接受的成对路径的附加门禁。

发布后只补文档关闭记录，不修改原 tag、已接受 APK 或原始验证/验收记录；另存发布阶段记录。未执行的阶段如实标注，不清掉失败证据。
