## 已确认问题

### A01 · P1：复用损坏内容块后，每日备份仍返回成功

位置：[repository.ts](../../packages/storage-indexeddb/src/repository.ts)，253–261 行；约束：[BLOCKCOLC.md](../../BLOCKCOLC.md)，107 行；[ARCHITECTURE.md](../../ARCHITECTURE.md)，73–75 行。

`createDailyBackup()` 仅通过 `getAllKeys()` 判断块是否存在，已有相同 ID 就跳过写入。内容寻址的 key 存在不等于块内容仍与 SHA-256 一致；这里没有核验已有内容，随后保存新清单、裁剪旧清单并返回成功。

实际复现：创建 7 月 23 日档，翻转一个已保存块的首字节，保持当前领域状态不变，再创建 7 月 24 日档。调用返回成功，目录只剩 7 月 24 日；立刻导出该档却报“每日备份内容缺失或校验失败；当前记录未更改。”新档继续引用损坏块，未能利用本次已经准备好的正确内容修复它。

影响：自动留档可能报告成功并替换旧索引，用户直到导出或恢复时才发现最新档不可用，违背“留档失败不标记保存成功”的产品规则。

建议：在提交新根前保证所有复用块的实际内容有效；若重写损坏块，必须使用本次已验证的正确内容，并与新清单的切换协调。若无法保证，保留原档并返回失败。哈希仍应在长写事务外进行，提交时保留并发校验，不应靠一次读取全部 200 MiB 内容解决性能问题。

应补回归：损坏未变块后次日捕获、同一天重复捕获、缺失块、修复失败及并发保存；成功返回的新档必须立即可独立导出和恢复。

### A02 · P1：新日期留档绕过升级校验，删除损坏的旧多日档及其余恢复点

位置：[repository.ts](../../packages/storage-indexeddb/src/repository.ts)，229、245–259、284–304 行；现有测试：[daily-backups.test.ts](../../packages/storage-indexeddb/test/daily-backups.test.ts)，85–102 行。

`compactDailyBackupHistory()` 的确在裁剪多日档前读取并验证最新根，但只有请求日期已经存在、重复写入或日期回退等分支进入该方法。正常请求一个更新日期时，另一条路径直接决定保留清单并删除旧档，未执行同一保护。

实际复现：准备 7 月 23 日、24 日两个旧档，破坏 24 日最新根，并确认它已无法导出；随后调用 `createDailyBackup('2026-07-25')`。调用成功，原来的两份档全部消失，仅剩 25 日。旧的有效恢复点也被删除。

影响：升级后的首次留档发生在新日期，是正常可能出现的场景；此时“先校验最新根，损坏则全部保留”的规则失效。当前状态的新快照不能代替被删除的历史恢复点。

建议：让所有会裁剪旧多日档的入口共享同一升级校验和并发保护，校验失败时不删除任何旧索引或内容块。该问题与 A01 不同：即使新档自身可读，也不能跳过对旧档的升级保护。

现有损坏迁移测试只请求已经存在的 `2026-07-24`，因此覆盖了安全分支。需同时覆盖晚于最新旧档的新日期，以及最新档缺块、内容被改和清单并发变化。

### A03 · P2：恢复领域数据后，旧自动轮次计划仍能向新基线追加完成记录

位置：[automatic-continuation.ts](../../apps/web/src/automatic-continuation.ts)，199–202 行；[round-plan.ts](../../apps/web/src/round-plan.ts)，479–486 行；[application-service.ts](../../packages/application/src/application-service.ts)，487–494 行。

应用服务在导入或恢复后发出 `replacement: true`，但自动连续协调器的订阅忽略事件内容，照常调和旧的本地计划。已结束的旧休息阶段可以被转换为 ready，保留原授权并以旧绝对时间补开下一轮；此路径没有确认旧计划引用的历史会话仍存在于替换后的领域数据中。

实际复现使用真实 ApplicationService、IndexedDbStateRepository、计划解析器和协调器：

1. 为同一项目导出尚无专注记录的备份。
2. 完成一个 1 分钟轮次，保存合法的三轮自动马拉松计划；计划处于休息阶段，剩余两轮已授权。
3. 时间推进至计划结束之后，导入第一步备份。刚恢复时历史为 0。
4. 协调器读取保留的计划并执行 `reconcile()`，新增两条 completed 记录，开始时间分别为 09:06、09:12。最终计划显示完成三轮，仍引用已被恢复操作移除的第一轮 ID。

影响：替换成功后的历史又被恢复前的 UI 上下文改变，轮次计数与当前历史不一致。本轮验证的是服务与协调器集成路径，未声称已通过完整设置页面点击复现；界面能否在特定沉浸状态进入备份操作未作为本项已验证事实。

建议：为数据替换定义明确的计划有效性边界。成功替换后，旧计划若无法与新历史对应，应停止其自动授权和原生待处理事件，不能仅因项目 ID 相同就继续补写。需处理在途回调、失败恢复和进程重启；失败的替换应保留原有可恢复上下文。正常重启继续已授权计划的行为应维持。

规则也需补足：[ARCHITECTURE.md](../../ARCHITECTURE.md) 47 行明确领域备份不含 UI 计划，但没有说明导入、回滚及每日恢复后如何验证或废止这些计划。应在原条目明确，不在版本日志中另立相反规则。

### A04 · P2：合法的大蓝图累积后，成功导出的备份无法被本程序导入

位置：[codec.ts](../../packages/storage-indexeddb/src/codec.ts)，13、32–45、73–76 行；[repository.ts](../../packages/storage-indexeddb/src/repository.ts)，104–111、328–330 行；[validation.ts](../../packages/domain/src/validation.ts)，169–255 行。

备份创建会校验领域结构并计算摘要，但不约束导出大小。普通导出和每日档导出都将完整领域载荷序列化；导入则硬性拒绝超过 100 MiB 的 JSON。每个项目包含自己的蓝图快照，导出格式不对相同快照去重。

实际复现：5 个合法项目各保存一个 60×60×60 的蓝图，每份 216,000 个普通橡木体素；调用真实 `createBackupEnvelope()` 通过完整领域校验并生成 64 位摘要。紧凑 JSON 为 **126,904,267 字节，约 121.03 MiB**。将此结果传给真实 `parseBackup()`，立即得到 `Backup exceeds the 100 MiB import limit`。复现未写入这份大文件，也未接触真实数据库。

影响：使用产品明确支持的蓝图尺寸，积累少量项目后就可导出一份不能恢复的备份。每日存储的 200 MiB 去重预算也不能保证完整 JSON 低于 100 MiB。

建议：统一“可保存数据”与“可恢复备份”的容量契约。优先评估可独立恢复、去重的版本化备份表示及有界解析；若短期限制导出，应明确报失败而非交付不可导入文件，但仅限制导出不能解决已有大工作区的恢复需求。不要直接取消所有导入上限。

应补回归：多项目重复蓝图、不同大蓝图、蓝图库与项目快照同时存在；对每个允许成功导出的代表性状态执行真实导入，确认达到完整往返。

## 覆盖边界与建议顺序
