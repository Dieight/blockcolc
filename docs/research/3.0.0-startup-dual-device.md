## 当前已确认的问题

### 用户预览误用了 Debug

原构建 6 虽然做了裁剪，仍是 debuggable 的 Debug 包。Redmi 上其 dex 状态为 `run-from-apk`；同源的非 debuggable 优化候选为 `speed-profile`。同一套优化代码的两种配置已经实测，配置差异足以显著改变启动时间。

已将 `recordUserPreview` 和包摘要工具改到 Release 输出，保留隔离预览原签名。交付检查会拒绝 debuggable 包；benchmark 只用于性能归因，诊断包仍单独构建。官方建议也要求性能测试使用接近正式版的[非 Debug 优化配置](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-overview)。

### JSON 与顶点读取存在重复成本

ART 采样显示大量时间花在 JSON 数字检查、完整状态树的重复解析／复制，以及逐标量读取顶点缓冲。采样改变了程序速度，以下是归因证据，不是用户启动耗时；同一调用栈的包含时间不能相加。

采样补正：早期把 `am profile --sampling` 的微秒误作毫秒，5／10 两份参数实际为 5／10 微秒；其中真实大库的 10 微秒文件已溢出。原 trace 和 `sampling-erratum.json` 保留，这些文件不作完整火焰图或启动耗时依据。后续改为 `10000` 微秒，42 秒 trace 无溢出、38,912 条记录、调用栈配对无误；仍只用于归因。R8 会合并类，解释方法名时必须配同一包的 mapping，不能按合并后的类名猜模块。无采样录像及呈现帧记录不受此参数错误影响。

已做的修改：

- 数字语法仍由严格扫描器检查，二进制数值转换使用 `Double.parseDouble`，不再为每个数字触发正则检查。
- 同一次状态采用只生成一份分离的 JSON 快照，任务、汇报、统计和蓝图库投影共享该次读取；没有引入可变全局缓存。
- 顶点／索引使用有界批量缓冲读取，仍检查全部数值、索引和仿射数据。
- 加载期间保留布局和世界预载，但不提前绘制被遮住的 UI、文字和天气；世界实际呈现后才打开界面。
- 方块状态、活塞、告示牌及营火校验使用相同的固定正则规则，改为复用 Pattern；原先每个属性重新编译的热点来自有效采样。
- 解码时有界复用重复字符串和小整数；完整语法、Unicode、重复键、深度及数值校验继续保留。蓝图库先生成元数据，打开预览时再读取几何。
- 计时控制和可选同步导出不再扩展建筑方块；存储复用核对真实行及资产摘要，超大文本绕过 CursorWindow 的单格容量，不截断数据。

纯 JVM 定点为领域 17、专注 34、界面投影 86、所选世界包检查 28 项通过。不是全量。附加备份与诊断构建另留原报告。

### 真实备份触发堆耗尽

Redmi 实际备份首次导入在 `DomainDocument` 生成规范 JSON 时耗尽 256 MiB Java 堆。导入器对刚解码、尚未交给任何外部调用者的私有树又做了一次深拷贝。

已把这一步改为明确转移解码树的所有权，保留校验、迁移、规范化和不可变文档边界。相同真实备份随后完成新库初始化与完整读回核对，原库未替换。诊断配置下这次准备耗时 51.157 秒，不能当成优化用户包的启动或导入速度。未用扩大堆上限或缩小数据规避问题。

### 完整数据仍然慢

上表的小数据提速不能代表迁移成功。复制 Redmi 的实际正式备份到独立实验库后，早期候选还暴露了 CursorWindow 溢出、备份根与上传投影重复扩展导致的堆耗尽，以及一次采用后的显示恢复错误。失败均保留，没有通过缩小世界或清除数据规避。

完成这些内存修正后，完整数据有一次约 24.04 秒显示世界，后续多次仍超过 30 秒。单独启用 512 MiB Java 堆的候选约 31 秒或未在录像期限内就绪，没有解决问题，正常构筑仍为默认堆策略。256 MiB 来自设备的 ART 进程堆配置，不是项目写死的限额；两机 `heapgrowthlimit/heapsize` 分别为 256m／512m，GPU／native 内存另计。参见 [Android 内存说明](https://developer.android.com/topic/performance/memory-overview)和 [largeHeap 文档](https://developer.android.com/guide/topics/manifest/application-element#largeHeap)。

当前候选 `400190d9…` 为构建 7、Release、非 debuggable、largeHeap 关闭、私人预览离线。相同真实备份、保留磁盘缓存、每次重开进程并停止另一个空闲方块钟后的有效样本为：

| 包 | 首次可见世界约用时 | 说明 |
| --- | --- | --- |
| 原生私人预览 7 | 31.77、33.38、30.99 秒 | `redmi-full-pattern7-heap256-isolated` 第 2／3 轮及独立补采 |

### 世界绘制负担

Redmi 的完整聚落、极简模式持续旋转实测：原生未限制物理渲染像素时约 15.61 FPS；按画质／密度限制世界目标、保持文字和最终输出为原生分辨率后约 19.95 FPS。旧版同类操作约 27.05 FPS。这里仍有样本顺序、系统状态和旧版闲置限帧的影响，不作严格单变量收益结论。SurfaceFlinger 按每个阶段的实际呈现时间过滤历史帧，单独记录世界 SurfaceView 与 UI；初次未过滤的尝试不作比较依据。

当前还不能称为整体性能优化完成。有效采样继续指向完整状态装配／校验、重复读取与世界准备，旋转则有较重的渲染／驱动开销。不能把 P2 的缓存读入收益换算成整个 App 的启动收益。

## 尚待结束的对照

- 两机相同真实数据的优化用户包启动、首转、持续旋转和页面交互。
- SurfaceFlinger 实际呈现间隔与界面帧分别取证，不以 `gfxinfo` 单独代表独立世界 SurfaceView 的速度。首次尝试的区间混入此前帧历史，保留原始数据，后续按每段边界过滤。
- 世界与最终输出目标已分离；本轮同帧玻璃与源颜色定点通过，完整界面与高透明度的体验仍不能仅凭帧率或 JVM 测试判定。
- OnePlus 残留的 shell 录屏进程已在用户授权重启后清除，重启后的旧版连续截图另存。最新候选的干净对照尚未补齐；用户已取走 OnePlus，当前不再操作，等待明确接回。它仍选在独立实验库，原库未替换，指针和临时偏好待接回后恢复。
- 结束后核对正式包、原生原库指针与临时文件／偏好恢复。P3 仍须用户重新体验，不能据小数据启动结果进入 P4。
