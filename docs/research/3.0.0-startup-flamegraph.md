## 火焰图和结论

[`flamegraphs.html`](../../artifacts/experiments/v3.0.0/p3-navigation-jank-20261101-c/flamegraphs.html) 可切线程、CPU／栈内墙钟、搜索和点击放大，并可导出 SVG。`flamegraph-review.json` 记录实际浏览器渲染、搜索、缩放与导出通过；预览图和 SVG 同目录保留。墙钟含消息循环和等待位置，不能把它们都说成业务计算；不同线程、父子函数也不能累加成启动耗时。

当前冷启动采样最大的 CPU 来源是世界准备线程。几个含子调用的采样 CPU 如下，不是互斥阶段：

| 调用 | 采样 CPU | 后续方向 |
| --- | --- | --- |
| `WorldAnimalPreparation.prepare` | 约 4.79s | 逐块物理分类、碰撞与出生准备 |
| `PickGeometry` 初始化 | 约 2.96s | 三角形边界和 BVH；避免退回大堆数组 |
| `OriginalStructureCompiler.compile` | 约 2.16s | 原创模型和组件准备 |
| `NativeStateStore.load` | 约 2.38s | 保留已做的按实际内容复用，不再视为唯一大头 |
| `PacketRenderer.loadGenerated` | 约 2.57s | GPU 建包、上传及动物运行时初始化 |

世界准备线程搜索 Matcher 的覆盖约为 17.9%。先把动物碰撞分类的后缀、不可行走名称、水判断，以及细节金属材质中的字面量正则替换为字符串操作；通用解析不改。9 项动物正式算法对照和原创结构检查通过。尚无新版本同条件的启动对照，不能把这部分采样占比直接当提速比例。

切页系统追踪中，主线程累计约 7.38s 在 `postAndWait`／绘图同步，重组约 0.27s。正在验证保留被不透明普通页面遮住的 Surface，暂停其绘制并禁用触摸／辅助入口；回到世界时保留原 Surface lease 和 GPU owner。测量候选 `80290001` 及源码已冻结，真实行为用后续诊断包核对，尚不宣称收益。

R8 合并名字按对应 mapping 解读，图中仅对明确对应的调用加提示。例如 `UiApplier.prepare` 在世界准备线程对应 `WorldAnimalPreparation.prepare`；`NativeResourceSpecialCompiler.prepare` 对应 `OriginalStructureCache.prepare`；actor 中的 `NativePreviewRelay.text` 对应 `ExactReadDigest.text`。不把这些运行时名字误读成 Compose 工作或网络上传。

### 192 MiB 海岸获奖扩建与逐阶段准备

大文件恢复通过后，再把 25 栋真实包内复杂蓝图接到实际工作区的三轮流程。`emulator-coast-report-stage-r1` 在首轮完成、奖励改变景观避让范围后内存不足，失败位于海岸珊瑚景观规划；11 份受控文件恢复。此前的纯备份往返不能覆盖这种世界更新峰值。

旧 CPU 景观现在像地形替换一样先退下，再准备新景观，屏幕上的旧 GPU 场景仍保留。珊瑚遮挡范围提前计算，避免逐点重复构造同一对象的矩形。相关规划／取消恢复／景观源对照 12 项通过。r2 越过原失败后，在平面几何的堆内数组分配处再次内存不足。平面属性、法线、重映射及输出改用任务内分配域，原 Float32 顶点／法线／UV 的源对照和分配器视图检查，以及工作区建包共 19 项通过；未放宽堆限或减少内容。

r3 仍在世界 CPU 准备阶段失败，最终诊断阶段为 `packets-root`；模拟器进程其后不在，未取得这一轮具体异常栈，不补猜结论。r4 在保留数据重新启动模拟器后复现，新增的主机持续错误日志确认：地标编译期间，平移体素副本的列表分配仍耗尽 ART。原始失败及受控文件恢复全部保留；这一容量路径尚未通过。

有界结构化阶段记录同时拆出了反复准备成本：r4 在开始专注、世界内容未变时，源蓝图复用约 0.46 ms、施工输入约 5036 ms、几何缓存约 3.55 ms。该夹具含 25 栋、79,972 个源方块，仅施工缓存的体素保守估算就为 24.41 MiB，超过 24 MiB 预算；按固定顺序扫描的 LRU 会把下一栋的条目逐一挤掉。现改为稳定保留当前所有者，溢出者暂不缓存，修改只替换自己，删除后按原规则裁剪，预算不提高。反复越界扫描、取消／修改、原包几何及工作区建包共 21 项检查通过。此结果解释诊断慢段，不是手机提速数字。

后续候选也把原创实例的变换／颜色／附加通道放入原分配域，并缩短树群平移副本和邻居索引的调用寿命。仍返验同一 25 栋、同一奖励流程；没有用缩小夹具、提高堆限或主动 GC 绕过失败。所有阶段和失败只进入诊断构筑，最终用户包继续要求无探针。

r5 的未变世界施工准备降到约 342 ms，但完整流程仍失败，不能据此称容量已修复。r6 在首次失败后另取堆转储，明确捕获动物查询去重集合的分配失败；转储只由测试显式启用，正常包不运行。分析使用 Android Studio 自带 Shark，原始大文件放在 D 盘。其逻辑保留大小不是 PSS；旧动物索引的 ID 哈希节点约占 11.15 MiB，地形源数组约占 17.41 MiB。

### 真实客户端 JAR 与 25 栋建筑的组合复核（2026-11-02）

按用户要求保留真实大文件的规模：采用本机原始 26.3 客户端 JAR（41,483,720 字节，SHA-256 `4508d006323f24fa02876310c192d739af56516eb259000ac50f0909a68c9a2d`），经主机私有临时路径送入 Emulator，不加入 APK。四种聚落仍各使用 25 份来源蓝图，随后海岸采用客户端材质并移除恢复原创。测试中的地形准备也已进入与实际生成线程相同的映射缓冲区作用域。

首轮在 480 秒的单方法总限时到达时失败；四聚落和客户端材质已经呈现，恢复原创还在 CPU 打包。不能把它记为通过，也不把这次取消时采集的堆说成 OOM：异常是测试超时引起的取消。客户端采用前 Java 占用约 182.5 MiB／上限 192 MiB，采用后约 164.4 MiB。原始堆保存在 D 盘；[失败回执与阶段数据](../../artifacts/experiments/v3.0.0/p3-navigation-jank-20261101-c/emulator-real-client-large-world-r1/result.json)保留。

Shark 的取消现场显示，原生打包器的临时资源表仍单独支配约 13.0 MiB，包括旧图集和外部模型结构；这张表只用于本次实体／回退成员判定，已改为本次结束后释放，下一次根节点开始前也先清空。旧 GPU 场景仍按完整换入协议保留。另将原创实例变换从逐实例分配三个 Double 数组改成每次 append 复用 16 个 Double，计算顺序、远原点处理、仿射和有限数检查保持。新检查覆盖 2,051 个实例、跨包分片、跳过成员、旋转／非均匀缩放和远原点，逐个 Float 位对照原不可变乘积。包路线及世界打包器 17 项、结构编译器的补充检查通过；完整同规模场景正在复验，不据此声称真机速度提高。

组合复核第二轮在原限时内完成（459.393 秒）。所有原规模场景均呈现，最后的原创恢复也完成，阶段占用、CPU 时间和清理回执见[结果核对](../../artifacts/experiments/v3.0.0/p3-navigation-jank-20261101-c/emulator-real-client-large-world-r2/assessment.json)。两轮仅各一份 Emulator Debug 样本，而且第一轮未完成，不能由总耗时计算性能提升比。相同大原件的系统提供器流式导入、索引重开、去重及删除随后单独通过。

实际按钮对照采用单独进程的原生 UI Automator 工具，与用户预览没有代码依赖；被测预览仍使用 R8、非 debuggable 和原来的无诊断入口。数据先在诊断构筑中写入新库，再更换为优化构筑。这样既能点真正的提交按钮并包含原有送达停留，也能继续使用当前实际世界的诊断阶段证据。外部工具只记录可见状态的观察上界，不能把它说成精确首个更新几何帧。模块按 [Android 官方多进程测量建议](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-overview)及[官方 self-instrumenting 样例](https://github.com/android/performance-samples/blob/main/MacrobenchmarkSample/macrobenchmark/build.gradle.kts)配置，以 `nativePerformanceChecks=true` 单独启用，不进入用户 APK。工具及手机样本仍待验。

### 优化构筑的按钮反馈与新冷启动归因（2026-11-03）

OnePlus 再次获准操作后，另留原私人 /8、测试包、11 份受控文件和原库事实。正式 /104 及好友同步未改；本节实验结束后按这份新恢复点交回。实际按钮夹具仍为 25 个项目、三轮待汇报，冷启动另用 16,153,090 字节的真实备份副本，不能混称同一输入。

原按钮脚本连续未找到送达文字，但独立截图序列明确拍到了“材料已送达！”和正常返回的工作台；数据库也只保存了一次三轮、50% 推进。这是自动检测与真实画面不符，不能写成送达从未显示，亦不能把失败脚本算成性能通过。`oneplus-stable-report-button-island-visual-r3` 仅作排错，截图采集期间的耗时不纳入对照。修正检测时主动刷新辅助树、保存实际读到的文字；汇报状态同时增加无障碍通知。正常测量还拒绝首次世界失败／未加载，并在返回后核对世界操作可用。

Emulator 的失败录像暴露了另一条路径：首次世界失败已放出工作台，后续汇报让世界重试，却又盖上全屏初始加载。现将初始工作台就绪设为本次挂载的一次性边界；已显示的操作不随世界替换／重试被收回。世界仍保留自己的加载与错误表面。这项修复与辅助树检测分别验证，首次失败的具体原因尚未归定，原录像和错误输出保留。

未开采样器的 `oneplus-current-large-cold-and-surface-r2` 三次完整绘制为 8.784／7.440／7.283 秒，30.2°C。此前 `6140608d…` 候选为 8.137／6.872／6.984 秒，33.4–33.5°C；本轮没有证明整体提速，不把温度较低当作可以忽略慢样本的理由。8 秒显示轨迹中仍含停手和约 30fps 静态动画，不当作纯旋转帧率。

`oneplus-optimized-large-startup-profile-r1` 使用优化构筑 `15f0331b…` 取得新的 ART 归因。系统完整绘制为 8.102 秒，采样 10ms、16,157 条、0 栈错位、未溢出。世界准备线程累计采样 CPU 约 3.94 秒，存储／业务线程约 3.68 秒；它们不互斥，也不能相加成用户等待时间。世界主要涉及场景打包、原创组件、源蓝图读取和拾取准备；业务线程主要是 SQLite 大文本读取、精确内容摘要与 UTF-8 校验。对应 R8 mapping 中的 `NativePreviewRelay.text` 实际来自 `ExactReadDigest.text`，不能据名字归因为好友网络同步。

这份 OnePlus trace 的墙钟字段与系统回执不一致：头部 `elapsed-time-usec=8360`，线程墙钟按协议解释也仅约 8ms，而实际过程为约 8 秒。没有擅自乘 1000 修正或据此报告空闲占比；现仅保留 CPU 采样的粗归因，墙钟／等待结论继续以有效系统记录为准。原 trace 位于 D 盘，摘要 `f0bd77952499273583b40bb08e88d95a12501f7f07c609c6ce5bcc2fa5f87cca`；采样运行不并入未开采样器的冷启动对照。

`oneplus-embedded-profile-startup-r2` 在每档前清掉当前／参考 ART Profile；后一档在启动 Activity 前，由接收器从 APK 写入清单，返回 1，再编译并核对实际 `speed-profile` 状态。APK `dbed3894…`，仍用同一 16 MB／23 项目副本；原件缓存保留，温度 29.1–29.3°C。

| 同包状态 | 三次完整绘制／ms | 中位数／ms |
| --- | --- | --- |
| verify | 7346／7431／7251 | 7346 |
| 仅随包 Profile 编译 | 6823／6793／6868 | 6823 |

中位数减少约 7.1%，这是清单被编译后的对照，不是手动侧载后的自然首启保证。仍只有每档三份、固定顺序；不与前一组不同温度／不同 Profile 来源的样本拼成新比例。六张结束截图已审看，归档 Profile 未压缩，输入摘要、APK 摘要和恢复事实由[独立汇总](../../artifacts/experiments/v3.0.0/p3-navigation-jank-20261101-c/oneplus-embedded-profile-startup-r2/assessment.json)核对。原无探针私人 /8、测试包及数据已恢复，正式 App 未动。

上一组“世界按钮可用”会把仍可操作的旧场景算进去，后续不能继续用它代表更新完成。现在世界的辅助阅读状态只在当前输入、资源和自己的 GPU 回执匹配后变为就绪。外部工具同时记录送达、工作台和当前世界三个终点，也允许世界按钮按原产品规则自动隐藏。
