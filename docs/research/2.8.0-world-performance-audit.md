# v2.8.0 世界建造与加载审查

日期：2026-10-15。状态：草案，审查完成、性能方案待确认；没有修改渲染或缓存实现。
关联需求：[本轮 UI 调整与性能审查](../versions/2.8.0-development.md#89-交付后的-ui-调整与性能审查)。

## 结论

现有持久缓存确实有效，不能把世界慢归结为“地形每次重新生成”。当前最值得补齐的是缓存之后的工作：景观仍重新建网格，外部材质包下建筑不复用常驻网格；部分“后台任务”仍是一整段主线程计算。

建议先减少重复构建，再引入 Worker 和可直接恢复的几何缓冲。暂不迁移整套引擎到 Rust、WebGPU，也不以减少装饰、天气或阴影换速度。

## 目前实际走的链路

入口是 [WorldCanvasV7](../../apps/web/src/WorldCanvasV7.tsx)、[renderer-bootstrap](../../apps/web/src/renderer-bootstrap.ts) 和 [voxel renderer](../../packages/voxel/src/renderer.ts)。

```text
冷启动：加载模块、读取材质选择 → 并行恢复场景与建筑 CPU 缓存
       → 创建材质图集／建几何／上传 → shader 与实际画面预热 → 开场
进度变化：复用同布局地形 → 遍历建筑与奖励 → 重建景观网格 → 呈现
切换聚落：更换 renderer → 可恢复对应空间缓存，但图集和 GPU 资源仍重新准备
```

天气与天文准备已和模块加载并行；上述步骤是依赖关系，不是可以直接相加的耗时表。场景和建筑缓存并行读取，但目前要在材质选择读取完成、调用 `initializeWorlds` 后才开始。

已有的优化应保留：

- 页面间常驻世界；同空间输入保留地形 GPU 网格；原创材质下部分未改变建筑可保留网格。切换光影档位已走常驻 renderer，不等同切换聚落。
- 独立的 64 MiB 场景缓存、32 MiB 建筑 CPU 缓存；类型化数组、共享方块引用和损坏回退已经具备。它们是缓存预算，不是 App 的总内存上限。
- `InstancedMesh`、树木分块及实例裁剪、珊瑚内部面剔除、地形共面合并、纹理图集和 mipmap 已经使用。
- `compileAsync`、远景／近景／两个旋转方向／恢复视角的实际预绘制，以及异步 GPU 完成检查已在加载阶段。不能把“再加一次预热”当新方案。
- 有低负载任务队列、渐进启动与隐藏页面准备；有条件的 GPU timer、重建阶段及帧间隔诊断也已存在。

## 本轮对照：直接生成与真实 IndexedDB 恢复

Windows 本机 Chromium 149，Pixel 7 视口模拟，未做手机 CPU 模拟。固定种子、V4 地形、`refinedFar=true`，每种场景三次。使用隔离的同源空页面，不启动 App、蓝图预览或其他 WebGL 世界；只读写临时测试数据库，不接触用户记录。

“生成”包含地形、紧凑地形网格与景观规划；“恢复”包含 IndexedDB 结构化克隆读取、解码和完整校验。**两者都不含景观／建筑 GPU 网格建立、图集、上传、shader、开场动画或 Android 启动。**

| 合成场景 | 生成中位数 | 恢复中位数 | 写入中位数 | 缓存预算估算 |
| --- | ---: | ---: | ---: | ---: |
| 1 栋海岛 | 982ms | 67ms | 30ms | 5.0 MiB |
| 24 栋海岛 | 1526ms | 83ms | 35ms | 6.2 MiB |
| 24 栋海岸 | 3375ms | 322ms | 297ms | 21.0 MiB |
| 60 栋海岸 | 5147ms | 389ms | 336ms | 24.7 MiB |

12 次恢复均通过全字段、数值和近远景共享引用等价检查。24 栋海岸的恢复范围 312–403ms，60 栋为 365–424ms；24 栋海岛的生成范围 1194–1862ms，样本仍有明显波动。64 MiB 预算能容纳这组海岸数据，不代表任何大型导入蓝图世界都能命中。

原始记录：[隔离测量](../../artifacts/verification/v2.8.0/post89-world-audit-20261015/cache-benchmark-isolated.log)、[诊断用例](../../apps/web/tests/world-cache-benchmark.diagnostic.spec.ts)。先沿旧用例的 App 入口跑过一轮，随后改为隔离页面并增加 60 栋；[前一轮记录](../../artifacts/verification/v2.8.0/post89-world-audit-20261015/cache-benchmark.log)保留，但不把两轮差值当优化收益。场景、页面和宿主负载与旧版记录不同，也不据此宣称版本回退。

本轮证明的是**现有缓存绕过生成的收益**，不是新实现的提速成绩。完整字段的规范化比较属于诊断成本，已单列在 `compareMs`，没有算入正常恢复。

## 以前手机实验能说明什么

以下来自 [v2.7.0 缓存记录](2.7.0-world-cache.md)和 [OnePlus 原始实验](2.7.0-device-performance.md)，不是当前 /89 手机复测：

- 10 月 12 日 /76 海岸两次启动：缓存读取约 271／350ms，规划约 0.1ms，但重建仍约 2.47–2.49s，其中景观几何约 1.81–1.84s。说明“规划命中”和“几何已就绪”不是一回事。
- 同日 /80→/81→/82 稳态海岸对照：仅减少树木 draw calls，rAF P95 仍约 42ms；再去除礁床内部面后约 25ms，主通道三角形约 215 万降到 101 万。更少的 draw calls 不必然提高帧率。
- 当时没有有效 GPU timer，不能把 rAF 或 renderer CPU 时间称作 GPU 时间；温度、实验顺序和后续素材修改也限制了对照结论。

本轮没有重启、安装或操作手机。当前版本的整次冷启动、MC 26.3 材质下的阶段占比和稳定旋转成绩仍需重新采样，不沿用历史秒数作保证。

## 查到的缺口与建议顺序

### 1. 先补常驻资源的增量更新

`renderer.ts` 的 `addBuilding` 明确要求 `!activeResourcePack` 才可保留网格。因此外部材质开启后，即使另一栋建筑毫无变化，进度重建时也不走这条复用路径。`rebuildSteps` 还会清空非保留建筑所在组，再为奖励和景观创建对象；景观缓存只避免 `planWorldScenery`，`addWorldScenery` 里的遮挡场、几何和批次仍重做。

建议把静态景观、奖励、施工动态分成独立资源层，先按整层身份复用，再按空间块替换变化部分。建筑复用扩展到外部材质，但不能直接删掉上述判断：复用身份须包括材质内容／图集代际，重新登记动画纹理、灯、遮挡、透明与阴影引用；标牌、营火等有专门生命周期。

主要收益应体现在提交推进、活动建筑变化和重复进入，而不是承诺进程冷启动零上传。进度显示、腐败、奖励新增、资源包替换和取消重建都要核对；引用计数及销毁必须跟上，避免用内存泄漏换速度。

### 2. 冷启动缓存进一步接近可绘制数据

现有地形缓存已含紧凑网格，建筑 CPU recipe 已含部分拓扑、矩阵和遮挡。缺口主要在景观与外部材质几何：读取到的是方块和布局，仍需把它们变成可绘制批次。

建议保存有版本的几何／实例缓冲及材质路由描述，直接恢复 `BufferGeometry` 和实例矩阵。先做静态景观和较大建筑，不把整套 Three 对象图写进数据库。GPU 句柄不能跨进程保存；上传、能力检查、动态光照和 shader 准备仍需执行。

生成算法、蓝图内容、材质内容、图集布局和几何版本分别入键。沿用可丢弃缓存及预算，旧版本或校验失败重建，不能影响正式数据或备份。

### 3. Worker 与有时限的分片，比先换语言更合适

目前没有 Worker 路径。渐进初始化只在阶段／建筑之间让出，整个景观组和一次图集解码仍可长时间占住主线程；普通 `setWorlds` 则同步耗尽生成器。低负载队列只决定何时开始，不会在旋转开始时中断正在执行的编码、估算或几何任务。

适合移出的纯工作包括地形、景观规划、遮挡／网格准备、PNG 解码与图集排布、缓存编码及校验。配合取消代际和最新请求合并；主线程只分批创建／上传资源。初始分片预算可从数毫秒试起，再按手机结果调整。

Worker 应传类型化数组，避免来回复制大对象树。转移 `ArrayBuffer` 会使发送方缓冲失效，不能转移仍被当前世界引用的缓存；可让 Worker 持有存储和生成中间态，只交出新缓冲。依据 [MDN Transferable objects](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects)。

`requestIdleCallback` 仍在主线程运行，超时也不是充分的空闲预算；需真正拆分任务，保留不支持时的后备路径。依据 [MDN requestIdleCallback](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestIdleCallback)。

### 4. 外部材质的存储与图集准备

常驻世界已有轻量选择版本去重，不再每次返回都读全部材质包。但首次读取和聚落更换仍读取包含原 ZIP/JAR 的记录；仓库校验复制 manifest 和 archive，之后图集又逐张解码。切换聚落会创建新 renderer，选择未变也重新准备图集。

建议先采集读取／校验／图集／上传各自占比，再决定：

- 将运行用 manifest／纹理与原始归档拆开读取；原件仍留给导出、重新解析和恢复。升级存储时保留完整校验与旧记录迁移，不通过跳过安全校验提速。
- 用材质内容与图集版本缓存已解码像素、mipmap、帧表；同一选包在环境重建时可复用 CPU 图集。不能仅按包名或 packFormat 命中。
- 场景缓存读取可与材质选择读取并行，但需控制峰值内存，不能只把串行等待改成无限并发。

当前图集已有峰值估算、页数和分辨率限制；缓存新增的解码副本必须计入同一预算，不能把磁盘缓存大小当显存占用。

### 5. 稳态旋转：继续减少无效几何，而非只合批

先分清 CPU 提交、顶点／片元、阴影和玻璃后处理的成本；新手机若仍没有 GPU timer，用各通道受控对照，不从一个 rAF 数字猜 GPU 时间。保留已有阴影刷新门控和按需绘制。

可以试块内不透明方块的可见面合并、按材质／拓扑批次和更细的视锥裁剪。地形已经共面合并，树木也已有实例裁剪，不从头再做一套。透明水／玻璃、叶片裁切、台阶、AO 和逐块纹理不能粗暴合并成实心面。

Three.js **本项目为 0.178.0**，已有 `BatchedMesh` 可用于同材质的不同几何，但不等于替换所有 `InstancedMesh`；须测设备的 multi-draw 路径、裁剪成本和透明排序。[Three.js BatchedMesh](https://threejs.org/docs/pages/BatchedMesh.html)；接口已和本地 r178 源码核对。减少 WebGL 状态变化、合理分批和显存预算依据 [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)。

另有两项应纳入下一次 CPU 样本：蓝图内容指纹只有冻结对象才记忆，未冻结对象会再次序列化、遍历全部方块；建筑 recipe 的 `put` 也重新遍历估算大小。先给不可变蓝图建立可信内容版本，再省重复遍历，不能退回只用 ID 判断缓存有效。

### 6. 暂不优先引入的技术

| 技术 | 判断 |
| --- | --- |
| Rust／WASM | 可用于已测出的纯数值热点；不会自动消除重复重建、数据库克隆、GPU 上传或驱动等待。先与 JS Worker 做同输入比较，再决定是否值得维护第二套实现。 |
| KTX2／Basis 压缩纹理 | 值得在纹理上传／显存成为主因后做小样；用户导入 PNG 还需编码，设备需选匹配格式，动画、透明边缘和图集 mipmap 都要验证。不是直接替换文件扩展名。[Three.js KTX2Loader](https://threejs.org/docs/pages/KTX2Loader.html) |
| OffscreenCanvas／WebGPU 全引擎迁移 | 可作后续研究；Android WebView 的实际能力、现有玻璃／材质 shader 和恢复路径都要适配，不应仅凭桌面浏览器支持就开始迁移。 |
| 通用压缩缓存 | 降低 IO 可能被解压／分配抵消。当前海岸 24.7 MiB 仍在预算内，优先省掉几何重建，再实测压缩是否划算。 |

## 后续验证办法

先做“未改景观／建筑不重建”的最小实验，再做 Worker 与可绘制缓存，逐步比较，不能把同时更换素材的结果算成纯性能收益。

- 输入：小世界、24／60 栋；原创／确切的 MC 26.3 包；海岛／海岸；大型导入蓝图；冷缓存、已完成写入的恢复和损坏回退。
- 操作：进程冷启动、首次旋转、稳定旋转／缩放、一次推进、增加奖励、切换环境／材质／光影、取消和快速往返。相同输入重复取样，记录温度和内存，条件允许时交错新旧顺序。
- 分项：缓存读／解码、布局、景观几何、建筑几何、图集、首次上传、预热、可用首帧、开场完成、提交到稳定画面；看 P50／P95／最大长任务，父子阶段不相加。
- 正确性：布局、随机结果、纹理／动画、阴影／倒影、拾取、施工轮廓、腐败、历史记录与退出恢复均不变；过期任务不能在后台覆盖新世界。
- 缓存／资源：命中与未命中分别报；检验淘汰、空间不足、内存峰值、旧 renderer 销毁、长时间多次切换，不用仅一次更快的样本验收。

## 本轮实施边界

只改了便签与备份 UI，诊断用例增加了独立页面和大世界样本；上面的性能改造均未实施。UI 验证与截图记录见开发日志。本轮没有全量、构建、发布或设备性能实验；本文件是下一轮选择技术路线的依据。

后续用户已批准尝试；实施和 OnePlus 新对照另记于[世界管线实机实验](2.8.0-world-pipeline-device.md)，不覆盖本次只读审查的原结论。
