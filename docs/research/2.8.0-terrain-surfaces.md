# v2.8.0 共享地表查询

2026-10-16。已采用源码改动，尚未出包。接续[地形审计](2.8.0-terrain-audit.md)，不改地貌、水系、建筑和奖励的布局规则。

## 重复工作在哪里

降水落点、奖励支撑、海床、景观和海岛阴影范围各自调用矩形提取。旧实现每次从顶面索引取四个点，再分配多层临时数组和矩形对象；奖励和景观还会各建一套字符串分桶。地形与景观已经缓存时，奖励支撑和海岛阴影范围仍会重复这些步骤。

这次先共享读取结果，没有改成分块生成，也没有把表强行变成新的存档格式。地形核心半径、LOD profile 和水文仍有全局依赖；相关调研沿用前轮记录，不把分块坐标当作完整身份。

## 采用的实现

- `TerrainSurfaceTable` 首用时提取一次，每行五个 Float64 和一个 Uint8，共 41 字节数值内容。保留原材质／顶面输入顺序和 `最高顶点 + 0.5` 的支撑基准，不能把水面改成整数高度。表迭代出来的是新对象，不暴露内部列。
- 奖励支撑与景观使用同一份按八格分桶的索引：前缀偏移加单元序号，桶内保留输入顺序。点查询只创建命中的记录，不长期保留整个地表的对象数组；景观规划需要排序／筛选时才临时展开。普通数组调用者仍建自己的索引，修改后另建采样器不会命中旧表。过大、极稀疏或无界输入回到线性查询，避免巨量分桶分配。
- 表与索引通过 WeakMap 跟随源几何身份。原始生成缓冲在 renderer 生命周期中视为不可变；新地形建立新表，旧地形不再被引用后可回收。公开的 `terrainSurfaceRectangles` 仍返回独立、可修改的新快照，并能反映诊断调用者对源缓冲的修改。
- 两份数值缓冲及少量元数据估算计入现有 32 MiB 地形驻留预算，紧凑网格也在同一预算内；没有另开无限表历史。32 组样本中，原本能保留的源地形和紧凑网格均没有因这项改动失去缓存资格。这里是数组内容与元数据估算，不是进程堆或峰值内存测量。
- 表不进领域、备份、Worker 消息或场景持久化记录。原始地形、紧凑网格和景观输出不变，因此场景缓存仍用 revision 3；从磁盘恢复后首用重建表。持久化体积和已有格式不增加。

同时发现并修复降水恢复问题：地形从磁盘命中后，旧代码把地形命中等同于落点纹理已经就绪，可能留下初始的 1×1 平地纹理。现在纹理独立记录就绪 key；首次恢复仍建立正确落点，后续同地形推进才复用。

实现约束维护在 [ARCHITECTURE](../../ARCHITECTURE.md)，不改产品规则或扩大旧世界迁移范围。

## 怎么比较

[实验脚本](../../packages/voxel/tools/terrain-surface-audit.ts)使用合成世界，不访问应用数据库。冻结原矩形提取和完整景观模块；降水／海床 helper 在改动前没有本地修改，从 Git 恢复原文时核对冻结 SHA-256，再转成独立参考文件。其他生成依赖逐个核对不变。重跑使用已有冻结参考和新的输出 tag，不重新把当前实现抓成旧基线。

四环境 × 1／24／60 栋 × 两种子，加山谷自动／粗远景、海岸粗远景和 60×60 足迹，共 32 输入。全部比较完整地表顺序、支撑查询、降水纹理、海床、景观和阴影范围；原始地形哈希与前轮 32 组也逐一相同。没有只比较数量或接受新的外观快照。

计时对象是首用地表后的 CPU 后处理：降水落点、289 个支撑点查询、海岸海床、景观和海岛阴影范围。首次提取和首次建索引算在里面；重复路径只测支撑查询及海岛阴影范围，模拟地形／景观没有失效时的消费。**不是世界总重建或 App 启动时间**，不含读取数据库、原始地形生成、网格构造、GPU 和原生系统。

四环境的 24 栋／默认种子／精细远景各预热后交替 A/B、B/A 五组，散列检查在计时外；其他输入各做一次完整等价对照，不用于推断 P95。运行期间未同时跑其他测试；没有锁定系统频率。海岸景观本身的波动仍较大，不把单次极值当收益。

以下是五组中位数，单位 ms；额外常驻量是共享表与索引的数组／元数据估算：

| 环境 | 首用后处理：原 → 新 | 重复支撑／范围：原 → 新 | 额外常驻 MiB |
| --- | ---: | ---: | ---: |
| 空岛 | 163.5 → 80.6 | 26.12 → 0.74 | 0.60 |
| 山谷 | 2175.2 → 1670.1 | 169.55 → 0.50 | 3.58 |
| 海岛 | 859.7 → 504.2 | 194.77 → 3.53 | 2.60 |
| 海岸 | 2272.6 → 2066.6 | 111.06 → 0.39 | 2.54 |

海岛首用后处理约减少 41%，海岸约 9%；最稳定的直接收益是省掉重复提取和重复建索引，不是景观规则本身变快。不是所有推进都会执行上述全部支撑查询，不能把表里的差值直接加到旧冷启动成绩上。

## 验证结果

- [纯测试](../../artifacts/performance/v2.8.0-terrain-surfaces-20261016/voxel-targeted.log)：14 文件、82 项通过。包含四环境旧完整地形哈希、固定景观结果、海床／降水／奖励支撑、LOD 接缝、湿地等高优先、负数／小数／精确边界、数组修改与共享表隔离、缓存格式和内存预算。
- [浏览器报告](../../artifacts/performance/v2.8.0-terrain-surfaces-20261016/browser-report.json)与[日志](../../artifacts/performance/v2.8.0-terrain-surfaces-20261016/browser.log)：9 项，6.1 分钟，自然退出 0，无失败、跳过或重试。真实 Worker／拒绝 Worker 回退均通过；磁盘恢复首次建立正确的降水纹理，之后推进复用；原创／微型导入材质、阴影／纹理引用、珊瑚面、24／32／48 栋海岛沉船及相机行为通过。
- voxel 与 Web 类型检查退出 0；持久化体积未变，表不混进编码记录。采样边界的补充断言另做小定点，不重跑未改动的整组。
- 实际审看海岸横屏、48 栋海岛和山谷截图：主体、海床、阴影和沉船仍可见，未见新缺面。原有礁床轮廓等视觉问题不属于这轮无损性能改造。

没有 Android 实验、全量门禁、构建、安装、上传或发布；构建号仍是 2.8.0 /96，手机与已交付 APK 不会随源码变化。内存峰值、手机启动／旋转和 MC 26.3 整包实机效果未在这批验证中测量。
