# blockcolc 原生重构总规划

日期：2026-10-20。状态：用户已确认阶段推进，P0—P1 开始实施。
关联：[v2.9.0 的 NATIVE-01—08](../versions/2.9.0-development.md)、[实施记录](../versions/3.0.0-development.md)、[当前任务](../TODO.md)。v3.0.0 为原生迁移开发线；现有正式工程的版本号与交付保持独立，不因立项递增。

## 先说结论

已经能回答“原生路线能不能做”的一部分问题，还不能回答“把整套 App 搬过去是否值得”。界面、部分计时规则、保存与短计划后台恢复已经接通；最大的缺口是生产世界的动态渲染、完整数据迁移，以及同画质下的整体验证。

建议停止继续横向增加样机，转为有阶段验收的一个原生预览工程。先过世界渲染这道最不确定的关，再投入完整业务和页面迁移。不是先重写完再测，也不再把每个细节都发展成独立项目。

本文最初用于整理证据和审阅。用户现已同意先做 P0、P1，P1 通过后接 P2；P2 完成后的集成测试取得实际收益才继续后续阶段。技术候选未因确认顺序而自动变成最终选型，正式 App 的既有行为仍以产品文档为准。

## 一、几个核心问题的答案

| 问题 | 目前能下的结论 | 还差什么 |
| --- | --- | --- |
| Android 原生界面能做吗？ | Compose 已接活动世界、双向模式切换和一条持久化专注流程；中文中间编辑的测试通道检查通过 | 完整正式页面、真实拼音候选输入、系统字号、无障碍及更多设备仍未覆盖 |
| Filament 能用 Vulkan 吗？是否更快？ | 能运行 Vulkan；但现有复杂场景的实际呈现没有胜出，GLES 在本机更适合作为下一步参考后端 | 现在固定在实验用的 Filament 1.56.0，资产和材质也非正式方案；真实实例绘制、GPU 瓶颈及可用版本需收敛验证 |
| 换语言能显著提速吗？ | 紧凑数据和减少分配确有收益，不能归因于语言。局部计算快，不代表世界或 App 快 | 完整原生世界、正式存储与界面一起运行后的同条件对照 |
| 液态玻璃能保留吗？ | 实时背景取景可行；本机系统合成模糊比逐帧位图复制更省内存 | 系统模糊不是现有液态玻璃的完整替代；折射、高光、多窗口、键盘和能力回退尚未验收 |
| 计时与结算能可靠迁吗？ | 一组正式规则已用当前 TS 执行结果逐步核对，保存失败、重复提交和恢复有反例 | 专注完整性、腐败、奖励、完整时区业务等还未全迁；普通模式 UI 也不完整 |
| 后台负计时／不续轮能靠原生解决吗？ | 原生可以独立落盘交接，减少对 Web 恢复的依赖；但不能绕开系统策略。本机冷唤起被 `oplus startup` 拦截已定位 | 长计划、深度空闲、跨日、重启、完整 OEM 通知视觉和其他厂商仍待测 |
| 旧数据能安全带过去吗？ | 已证明当前格式的只读读取、原文保留、原子替换和回滚可以接通 | 完整语义校验、受支持旧 schema、正式写回及大容量场景未完成；现在不能拿样机导入用户数据 |
| 移动房屋会不会更容易？ | 可变换的建筑节点、稳定 ID、占地和局部更新接口会让它更容易；关键是架构，不是 Kotlin 或 Vulkan 本身 | 没有完成房屋移动实验。迁移只预留能力，不把“可移动建筑”顺带加成本版功能 |
| 是否该直接迁整套再测？ | 不建议一次性重写。可以从现在开始收拢成可持续开发的原生预览版，按阶段补齐 | 世界和完整存储尚有硬风险，过关前不承诺最终切换或整体性能倍数 |

### 最值得记住的几组数据

- **复杂世界并未证明原生更流畅。** 同一冻结 PBR 子集、25 栋、720×960 的分片合批对照中，海岸实际呈现为 Web 50.5、GLES 37.2、Vulkan 32.1 次/秒；海岛为 45.6、40.0、37.2。它们有画面差异，也没有完整动态动物／天气，不能直接排名最终技术栈，但足以否定“换原生必然更快”。见[实际呈现与资产布局](2.9.0-native-followup.md)。
- **内核提速不等于启动提速。** 12 万体素的独立内核，当前 TS／紧凑 TS／WASM／ART 汇总为 433.0／201.0／116.3／296.18ms；而真实海岸 renderer 里的表面函数虽减少约 35%，初始化中位数只变化约 0.8%，样本区间重叠。见[计算对照](2.9.0-native-complex.md)和[实际占比](2.9.0-native-followup.md)。
- **组合流程已可运行，但不是正式 App。** 正式 Oracle 覆盖 129 个命令步骤、555 组排程／时长；系统模糊相对位图取景少约 68／81 MiB PSS。世界仍是冻结输入，不能据此说原生冷启动已降到半秒。见[规则与玻璃](2.9.0-native-focus-port.md)。
- **备份优化主要来自去掉重复工作。** 约 1.41 MB 输入、2.90 MB 展开样本，原生读取从 2,890.61 降到 1,013.65ms；不是 TS 与 Kotlin 的性能比较，也不含完整校验或磁盘成本。见[只读备份](2.9.0-native-backup.md)。
- **本机后台拦截已有因果证据。** 同一 APK 开启自启动、保留智能优化后，Home／SIGKILL 的短计划均完整保存三轮，最大阶段迟到分别为 25／768ms；关闭自启动时系统明确跳过接收器。仅适用于该手机的这组短计划。见[最终权限对照](2.9.0-native-startup-policy.md)及[机器汇总](../../artifacts/experiments/v2.9.0/native-startup-summary-final/report.json)。

各轮测试会复用和扩充同一套用例，不能把历轮计数相加当作覆盖率。旧失败报告保留，不改写成通过。实验后隔离样机的自启动、通知和后台耗电开关已恢复；正式 App 与数据未动。

## 二、为什么这一段显得乱

前面的实验解决了不少真实风险，问题在于没有一个明确的项目级收口：

1. 从三个技术小实验逐步走到渲染、业务、备份和 OEM 策略，但“这一阶段做完到哪里停”没有先定。每次解决一个问题，又顺势追加下一项。
2. 冻结世界、合成计时、局部正式规则和只读备份，各自的完成标准不同；汇总时容易让人误以为已经接近一个完整原生 App。
3. 独立内核、绘制提交、屏幕呈现和正式冷启动混在一条讨论里，数字虽都有记录，却不直接回答同一个问题。
4. v2.9.0 的交付和未来迁移一直放在同一批当前事项里，缺少单独的总入口和版本边界。

这次不再补一份逐轮实验日志，而是把范围、顺序、退出条件和待决定事项放在本文。原报告继续作证据，不承担项目排期的职责。

## 三、重构范围与不变的东西

目标是把 Android 日常使用转到原生宿主、原生业务执行和原生世界，保留现有能力与已确认的视觉。Web 不作为新功能发布目标，但已有 TS 规则、测试和导出工具继续作为迁移参考；达到替代条件后再退役运行代码，不在一开始删除旧工程。

**迁移与 UI 再设计分开。** 本次先复现已确认的普通／极简布局、交互和像素玻璃风格。因为平台差异必须调整的部分单独说明，不顺带重新设计全 App。

| 范围 | 必须保住的内容 |
| --- | --- |
| 专注业务 | 普通／习惯、固定轮次／截止时间、三种展示与结算流程、手动等待、自动续轮、完整性、退出检测、提醒、恢复与幂等 |
| 任务和记录 | 项目／小任务、便签、今日目标、统计归属、纪念建筑、成就、腐败与修复，不猜测历史未知数据 |
| 世界 | 四聚落、V4 地形与种子、道路／地基、装饰、动物、LOD、缩放／选轴、建筑记忆、施工及局部更新 |
| 表现和资源 | 原创／26.3 外部材质与模型、透明和动画纹理、阴影、水面／玻璃、天气天象、夜空、面板效果、蓝图库及有界 Litematic 导入 |
| 奖励和附加功能 | 每日／节日／生日奖励及各自去重、庆祝、音频导入和雨声、随机留白、教程、中英和两种字体、主题与减少动态／透明度 |
| 数据与平台 | 完整备份、每日差异合并和操作回滚、升级迁移、文件权限、现实天气、位置缓存、后台音频、应用更新、OEM 通知与私有同步 |

这张表是迁移范围，不表示现在已实现。实施前用当前产品文档和代码补成可逐项验收的清单。

v2.9.0 仍是当前正式开发线：/100 私人包已有定点和配对构建，未跑发布全量；其后夜景／稀疏路灯源码尚未重新封包。迁移不能让这些改动丢失，也不能把 /100 当成已经发布。迁移对照基线应固定为用户最终接受的 v2.9.0 候选及其输入摘要；此前测量保留，不重复跑未受影响的旧微基准。

## 四、建议架构：明确职责，不先堆框架

| 层 | 建议做法 | 边界 |
| --- | --- | --- |
| Android 宿主与页面 | Kotlin＋Compose；页面接收只读状态并发出操作 | 主线程管交互和绘制，不解析大备份、造地形或持有第二份计时事实 |
| 业务与协调 | 纯 Kotlin 领域规则；一个串行命令入口，保存成功后发布结果 | 页面、服务、闹钟和恢复都走同一执行器；普通／极简不各写一套结算 |
| 存储 | 优先评估 Room／SQLite 保存业务和引用，不继续把全部大对象塞进一个样机原子文件 | 具体表结构在第一阶段确认；不能把“用了数据库”当成已证明更快 |
| 世界数据与派生缓存 | 与引擎无关的地形／布局／体素描述，独立计算队列和带版本缓存 | 稳定坐标、来源 ID、算法版本与资源身份可核对；坏缓存可丢，原始蓝图和业务不能丢 |
| 世界绘制 | Filament 作为候选，单独渲染线程；先以 GLES 为参考，保留可切后端 | 不承诺 Vulkan 默认；真实实例、材质池、分块和局部更新通过后再确定正式路线 |
| 系统与私有能力 | 复用并整理现有 Java／Kotlin 的通知、音频、天气、下载与文件能力；私有同步仍独立模块 | 不重写已可靠的原生适配器；标准包仍排除私有实现和配置 |

以下是需要先写清的几项契约：

- **事实、安排、展示分开。** 活动会话和历史是业务事实，自动授权与替换代次是恢复控制，倒计时只是投影。原生版可将它们在同一数据库事务内更新，但导出备份仍按原有范围，不擅自加入 UI 计划或复活自动授权。
- **大资产与小记录分开。** 蓝图和可复用内容按身份存放，业务记录引用它们。若内容放文件，先写完并验证再提交数据库引用，崩溃只留下可回收孤件，不能留下指向半文件的有效记录；不能假称数据库和文件天然原子。
- **世界是派生结果。** 地形、建筑 CPU 几何、材质、GPU 资源分别拥有生命周期。计时文字变化、动物活动、切页面不触发世界重建。推进只使受影响的建筑及相关遮蔽／碰撞失效。
- **资产复用不靠十万普通节点。** 保留真实实例和分块裁剪，对不同天气／腐败等可变材质状态明确分组；不直接采用实验中约 500MB 的冻结 GLB 包，也不强行共用所有材质克隆。
- **玻璃能力可回退。** 系统模糊是候选优化，不等于已通过设计验收。先验证同一活动世界上的玻璃、键盘、弹页和导航；不能用系统能力不可用时的透明底色掩盖文字不可读。
- **后台受限要诚实表现。** 沿用绝对时间、事件代次和持久化幂等；授权受限时停止过期倒计时并保留恢复入口，不以逐秒服务、常驻唤醒锁或音频保活绕限制。

不先引入 Rust／C++ 重写全部计算。只有完整流程的采样指出仍被某个内核拖住，才为它增加薄接口，并计入复制、桥接、构建和维护成本。

页面／数据分层和单向状态参考 [Android 架构建议](https://developer.android.com/topic/architecture/recommendations)。Room 的迁移需要显式路径和测试；正式数据不走破坏性重建，见[官方迁移说明](https://developer.android.com/training/data-storage/room/migrating-db-versions)。Filament 的[后端与构建资料](https://github.com/google/filament)说明能力，并不替我们的性能背书。正式依赖版本、SDK／最低系统、ABI 和原生库的 [16KB 页兼容](https://developer.android.com/guide/practices/page-sizes)在架构收口阶段确认，不直接沿用样机 1.56.0；若要缩小现有设备支持范围，另请用户确认。

## 五、按什么顺序做

各阶段由当前代理独立完成。只有一个活动工作包；世界、业务和平台可以分模块设计，不再同时铺开多个无人收口的实验。阶段验收后的推进边界随用户对本规划的确认确定；涉及技术路线改变或未达门槛，停下报告，不自行扩展重构范围。

| 阶段 | 做什么、交什么 | 完成条件 |
| --- | --- | --- |
| P0：定范围和基线 | 固定行为／资源／数据清单，核对文档与源码差异，冻结对照数据、采样边界和目标；确认原生工程位置、依赖版本和存储设计 | 每项产品能力有迁移归属；旧实验标出可复用／仅作参考；没有把样机限制当正式规格 |
| P1：先过原生世界关 | 在同一个原生预览工程实现引擎无关输入、真实实例／材质复用、动态相机、阴影、透明水／玻璃；先做海岛和最重的海岸 25 栋，再补天气与动物代表负载及一个建筑局部更新 | 画面经审看，实际呈现不明显倒退；资产与内存有界；操作不重建整个世界。不能只显示冻结 GLB 就过关 |
| P2：完整数据和计时闭环 | 扩充正式规则对照，接完整可写存储、导入／导出／回滚、原生后台和通知；在 P1 的活动世界上走选择任务→专注→休息／等待→汇报→建筑更新→统计→重启恢复 | 完成事实、统计归属和奖励一致；保存失败可恢复，旧事件／重复提交无副作用；一次真实日常流程可用 |
| P3：补齐全功能预览版 | 按范围表迁剩余页面、聚落、素材和系统能力；逐项核对普通／极简、双语、IME、玻璃、音频、权限与 OEM 降级；新增账户／好友／云同步和单份云备份 | 功能矩阵不再依靠样机替身；可导入复制数据并持续使用，主要视觉和操作由用户体验确认；新增范围见专属工作包 |
| P4：整体收益与切换候选 | 以最终 v2.9.0 基线作同数据、同画质的集成对照；完善升级桥接、安装身份、回退工具与原生门禁；验多设备冲突、权限／云恢复和原看板交接 | 性能目标达成，数据转换及恢复演练通过，统一候选正确承接既有标准／私人用户；未过关不替换正式版 |
| P5：发布与退役 | 经用户确认和所授权门禁后发布统一客户端，再清理旧运行时及客户端私人上传模块 | 统一包可覆盖升级且数据完整，旧包、可恢复备份与证据保留；Web 退役不等于删除规则参考和历史 |

### 两道必须提前看的关

**P1 不过，就不投入全量页面和业务重写。** 首先处理真实实例、资产创建和 GPU 提交的主要瓶颈；同一个问题最多先做两轮有明确假设的对照。仍不合格时提交原因、代价和备选路线，由用户决定保留现引擎、调整目标或继续原生渲染，不默默再开一串引擎实验。

**P2 完成后就测一遍整条流程的成本。** 不等所有设置页和装饰细节都迁完才第一次比较。若主成本只是从 Web 搬到原生、没有明显净收益，先调整数据／渲染架构，再补后续功能。

接下来不单独补做“所有后台长场景”再开始整体工程。这些场景安排在 P2 的同一正式执行器和存储上验证，避免先把样机磨到很完整，迁入工程后再验证一次。

## 六、数据怎样迁、怎样退

1. **预览阶段使用独立包名和独立数据目录。** 不将实验包覆盖正式安装，不让旧 Web 与新原生两套执行器同时向同一事实写入。现有样机只挑已核对的模块迁入，原代码和报告保留，不直接改名为正式工程。
2. **先复制，再转换。** 先支持完整正式备份的校验与导入；保留原件并列出转换摘要。任务／会话／汇报／奖励及蓝图内容逐项核对，未知字段和不支持格式明确拒绝，不能靠填默认值丢数据。
3. **正式升级需要单独的桥。** 原 App 的 WebView／IndexedDB 不是 Room 数据库，不能只换 APK 就当它已迁好。用最小、受限的旧数据读取入口导出所需业务、偏好、素材引用及有效恢复上下文，在临时目标库完整验证后再切换；步骤有标记，可中断重试，不删旧数据。过渡读取器不作为新 App 的长期 UI 运行时。
4. **当前格式与历史兼容都要列明。** 当前领域为 schema 15，封套为 1／2，兼容标识仍是 `tomato-clock-backup`；保留现有 100MiB 输入／512MiB 展开预算和每日合并／操作回滚语义。样机的 8MiB／32MiB 限额不继承。受支持的旧备份迁移单列测试，不恢复 V1—V3 地形生成器。
5. **自动继续不能由历史猜出来。** 备份导入／回滚提高替换代次、撤销旧授权；正常同机升级若有有效计划，则完整迁移并按既有授权恢复。数据损坏显示恢复入口，不转成强制首次创建。
6. **回退分清两件事。** 独立预览期间，原 App 数据完全保留；正式切换后的新数据不能假定旧版能读，也不能承诺 Android 可直接降版本安装。候选阶段必须演练兼容导出与恢复；退回旧实现需要更高构建号的恢复包或明确的数据转换路径，不能靠卸载。
7. **最后才接正式身份。** 最终包名、签名、递增版本号、文件权限和天气证书绑定沿既有升级链核对。2026-11-15 用户确认账户体系上线后统一客户端，既有标准／私人安装都要能升级；外部转发地址、账号映射和凭据只留自有服务器。切换前保留原双通道交付边界，不提前停用既有服务。迁移调试、原始用户数据和凭据不进正式包或公开报告。

## 七、性能怎样算进步

下面是建议验收目标，尚未达到，也不是对新技术栈的性能保证。P0 固定基线和预算后再执行，不用安装扫描、调试包大小或一次最快结果计算提升。

### 固定比较条件

- 同一设备、同一数据、同一可见画质、同一输出分辨率和镜头轨迹；匹配天气／时间、阴影、材质及已就绪的动物，保留温度和前后台记录。其他设备结果另列。
- 四聚落至少检查基本负载，主性能对照用海岛／海岸 25 栋，覆盖原创和用户本地 MC 资源包；轻场景作负控制，不用简化世界代替正式复杂场景。
- 进程冷启、进程内再次进入、派生缓存命中、失效重建分别采；不清用户数据来制造“冷启”。下载、安装扫描、权限页与正常启动分开。
- 端到端启动每组先取五次有效样本，报告逐次值、中位数和范围；短组不包装成可靠 P99。旋转／缩放用固定时长窗口收实际呈现，明显分歧才针对性加样。

### 分开记录五件事

| 指标 | 看什么 | 建议门槛 |
| --- | --- | --- |
| 冷启动 | 首次可交互 UI、世界首个实际显示帧、全部必要准备结束分别计时；包含业务读取和真实资源准备 | 缓存命中后的世界完整就绪中位数较基线至少降低 25%；失效重建中位数不恶化超过 10% |
| 进入后的卡顿 | 首次旋转／缩放、切页、前后台与通知栏恢复，不把“加载结束”只定义成第一张图 | 就绪后不再有可重复的百毫秒级主线程阻塞；稳态呈现间隔 P95 不恶化超过 10%，同时看掉帧和长帧分布 |
| 专注操作 | 点按开始、休息交接、汇报落盘到有效 UI／世界反馈分别记录 | 即时忙碌反馈目标 100ms 内；主路径的保存后反馈 P95 不比基线慢，不靠提前显示成功达成 |
| 内存与资源 | 峰值／稳态 PSS、Java／native／GPU 可得数据、切换后的释放、资源包体积 | 不以明显增加稳态内存换取达标；真实实例和按需资产不能退回十万节点或整包冻结场景 |
| 持续与后台 | 长时前台旋转、息屏多轮、进程重建、深度空闲、跨日／时区变化、权限拒绝 | 业务零丢轮／重复轮；系统受限时有明确回退，不把正常 force-stop 当后台准时执行；功耗另用有效采集，不拿充电温度代替 |

若整体就绪只快一点、帧率或画质明显下降，就不因为局部函数快了几倍而认定迁移成功。功耗、低端设备或 OEM 视觉没有可用设备证据时明确标未验收；影响发布范围的缺项由用户决定，不以 OnePlus 一机代表全部安卓。

## 八、后面的开发怎样保持有序

- **只认一个总入口。** 本文管待确认的迁移范围和阶段；确认后采用的模块约束才更新到 `ARCHITECTURE.md`，实施记录写入对应版本开发文档，`TODO` 只留当前阶段与链接。
- **每个工作包先写四项。** 要解决的问题、会改的模块、完成条件、失败／回退方法。一次只推进一个，做完核对遗漏后再开下一项，不用“继续”无限扩大本阶段。
- **实验必须服务于决策。** 写清两种结果各会改变什么；不改变路线的微基准先不做。旧基线有效就复用，算法对照、渲染对照和全 App 对照分开记录。
- **复用可靠代码和反例，不复用样机限制。** TS Oracle 随源码指纹更新；已有 JVM／设备回归保留。合成计划秒数、冻结世界和实验文件格式不自动进入正式实现。
- **验证随阶段走。** 平时做受影响定点和集成路径；用户明确要求全量时才跑完整门禁，规则仍依 [TESTING](../TESTING.md)。长测试自然退出后集中处理，不反复盯进度。文档审阅不触发应用测试或构建。
- **原生门禁要真正接好。** 业务 Oracle、数据库迁移、Android 界面／恢复、世界画面与资源释放各有对应入口；同步调整构建、配对、探针排除和发布工具。旧 Web 全量不能替原生页面背书，旧实验的通过计数也不能充当新工程全量；首轮收集完整失败、返修后遇错即停的既有流程不变。
- **证据与工程分开。** 每阶段一个简短实施记录和一个有效报告索引，原始失败保留。等新工程能替代对应实验后再按工作区维护规则归档，不在本轮删旧工程、旧 APK 或原始素材。

## 九、已确认的推进范围

1. 采用“先原生世界关卡，再数据与计时闭环，再全功能预览版”的顺序；先做 P0—P1，P1 通过后接 P2，P2 的集成测试取得实际收益才继续后续阶段。
2. Kotlin／Compose 作为页面和业务的首选；Filament 保持候选，GLES 作为下一轮参考，不预设 Vulkan；Room／SQLite 是待确认存储方案，不先全量引入 Rust／C++。
3. v3.0.0 以替代现有 Android 功能和可验证的性能收益为目标，不同时重做 UI，也不附带房屋移动等新功能；v2.9.0 交付单独收尾。
4. 接受以上可调整的性能门槛，以及先独立预览、完整迁移验证后再切正式身份的方式。
5. 2026-11-15 用户新增并确认[账户、好友、双向云同步与单份每日云备份](3.0.0-account-friends-cloud.md)。设备偏好同步，导入材质包／音频不同步；首次使用可登录恢复云端；最终客户端统一，由自有服务器转发原私人数据。同账号一台执行专注，其他设备查看或接管。此扩展已纳入 P3，公网 TLS、只读外部好友与账户页面已有定点。11 月 16 日按用户确认的真实备份补完返修，记录见 [P3 最新收尾](../versions/3.0.0-p3.md#2026-11-16备份返修与账户交接)。
6. 用户最新授权：P3 功能和返修完成后直接进入 P4 测整体性能，不再另等一次阶段批准。完整世界、操作与帧表现按上文门槛实测；资料完整后才交接旧来源。正式身份替换、发布及 P5 仍分别按授权执行。
