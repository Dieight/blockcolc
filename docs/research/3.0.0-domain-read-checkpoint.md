# 原生领域读取检查点

2026-11-03。接续 [启动反馈](3.0.0-startup-feedback9.md)。先做定点实验，再依据实机结果决定采用范围。

## 为什么继续做

移除重复读取后，16 MB 真实备份的普通／极简核心入口仍约 1.4 秒。首次开始专注已降至约 0.8–0.9 秒，但冷进程仍须把全部方块文本恢复为对象、校验并重新写出规范文本。已有的连接印记只在同一进程内有效，不能减少这段冷启动工作。

## 实验办法

保存完整领域文档及其只读索引，不保存第二份计时状态。读取仍检查 SQLite 的实际元数据、记录、资产和恢复字段；检查点必须匹配这些实际内容的摘要、领域摘要和当前校验器版本。匹配后使用保存的规范文本及索引，恢复上下文仍重新读取、解码并校验。

检查点采用 HMAC 认证，不能靠文件名、revision 或自报 SHA 直接信任。Android Keystore 只包装一个随机的认证密钥，大文件认证在应用内完成；系统密钥不进入备份。密钥不可用、认证失败、校验器变化或任何内容变化都回到原有完整路径。Android 的系统密钥操作会交给系统进程执行，包装小密钥可避免逐块传递整份领域文档，依据 [Keystore 说明](https://developer.android.com/privacy-and-security/keystore) 与 [AES/GCM API](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec)。

检查点属于可丢弃缓存。写出在独立队列进行，只接已验证的不可变文档；保留两份有界条目，文件原子替换。原库和备份格式不变，不把写缓存放在成功回执之前。冷启动命中、首次未命中、失效和损坏分别记录，不能只公布命中结果。

## 验证顺序

1. 编解码往返、错误密钥、内容篡改、截断、旧版本、错误索引和来源摘要不匹配。
2. 实际 Android SQLite 对照：有效命中与原完整读取结果相同；数据库改动和缓存损坏均不能掩盖损坏记录。
3. OnePlus 无采样冷进程测核心控件和实际首次操作。命中收益明显且恢复边界通过后，才接入默认启动。

## 已取得的结果

模拟器以 192 MiB ART 堆、实际 16 MB SQLite 输入、两个独立进程及真实 Android Keystore 测试。首次完整读取 28,464 ms，认证检查点读取 2,414 ms，条目 16,215,795 字节。篡改缓存后的完整回退与修复、同 token 数据库变化拒绝、恢复字段重新校验和独立密钥清理均通过。记录在 `artifacts/experiments/v3.0.0/p3-feedback9-fast-start-20261103/emulator-domain-checkpoint-r1/`。这是 Debug 模拟器存储对照，不是手机冷启动收益。

默认启动接入后的 OnePlus 无采样构筑 `feedback9-fast-core-benchmark-r5`（`e19a0892…`）实际命中检查点：普通核心入口 1,339 ms、点击到专注操作区 637 ms；极简入口 1,374 ms、双击到操作区 803 ms。输入与前轮相同，verify 编译，测试后原 APK、受控文件和领域／恢复事实已核对恢复。命中由原缓存同 inode、同摘要及启动期间读取触碰共同确认，不能仅根据文件存在判断。

存储局部改善没有等比例转换成整体启动收益，0.5–1 秒目标仍未达到。下一步区分剩余应用成本与无障碍观测成本：保留原入口测量，另外记录 Android 的核心 fully drawn 时间，并在独立冷进程中定时发送真实触点；只有实际操作成功才记录可操作时间上界。两种结果分开，不能改口径覆盖旧数据。校验器还绑定核心构建配置，密钥包装关联系统指纹，依赖或系统变化后重新走完整校验。
