# /9 反馈与第二轮启动审计

2026-11-03。接续 [P3](../versions/3.0.0-p3.md) 和[上一轮火焰图](3.0.0-startup-flamegraph.md)。本工作包覆盖新增反馈和启动目标。P3 原有收尾另列，原失败、音频补验和未完成的偏好重启实验均保留。

## 本轮要求

1. 室内取景以建筑区域为主，适当带入周边，不为完整主岛退得过远。
2. 补迁普通和极简冷启动的连续镜头开场；不能只设一个静态缩放值。
3. 修其他页返回计时页的掉帧。
4. 节日奖励详情显示具体节日。
5. 正式与迁移版各取冷启动归因；删除渐进启动设置，原生启动始终渐进。目标是冷进程启动后 0.5–1 秒内核心功能可流畅操作，世界后续补齐。首个占位帧不算操作完成，不能只提前报告 fully drawn。
6. 修 Home／后台返回后世界中轴偏移，核对两种复位和实际相机状态。

## 验证边界

- 初次启动、已有数据冷启动、后台恢复分别判断；对照使用明确的 APK、数据规模、缓存与编译状态。
- 分别记录实际核心操作可用、开始／切任务／设置的响应，以及当前世界首帧与完整交互就绪。后台生成不得占用主线程，亦不能把首次点击的慢工作移到按钮后。
- 真实大文件和中型日常数据都要覆盖。查清迁移新增的读取、校验、目录、投影、页面预热、CPU 建包及 GPU 采用，不将不同线程 CPU 相加成启动墙钟。
- 普通计时、极简及未结束计划恢复都保留正确任务与计时。读取失败保留原件，未核验的数据不能被假就绪状态采用。
- 性能采样与无采样计时分开；批次自然结束后集中检查。控制温度，主体分析和大文件留 D 盘。

## 当前证据

OnePlus 当前正式身份为 `com.blockcolc.app` /104（SHA-256 `c5dee73e…`），原生为 `com.blockcolc.preview` /9（`d425ea19…`）。两份原 APK 已核对摘要并另存 D 盘。正式包没有 shell profileable 或 WebView 调试入口，首次只打开检查可用采样通道，不是冷启动样本；没有更换正式包。归因将区分原安装包的系统记录与同源隔离参考包的调用栈，参考包运行资源必须与 /104 标准包核对，不能将其说成原安装包原位采样。

源审计已确认：`NativeWorldNavigation` 只在构造时取 `.45` 初始比例，没有开场镜头时间轴；`NativeWorkspace` 的默认入口仍等待世界和三页准备，渐进分支取决于旧偏好。室内拟合使用全部 orbit targets 和固定源 aspect，实际建筑范围、奖励远点及手机投影窗口需要分开核对。后续结果写在本文件，不将代码线索先认作全部根因。

证据目录：`artifacts/experiments/v3.0.0/p3-feedback9-fast-start-20261103/`。本轮修改和冷启动目标的最新核对见 [OnePlus 实机补验](#oneplus-实机补验)。P3 整体仍待用户体验，未进入 P4。

## 检查点和开场返修

检查点的真实 Android 存储完整性实验已通过，接入后的 OnePlus 普通／极简入口为 1,339／1,374 ms，首次专注为 637／803 ms；命中和数据恢复均有原始记录，详见[检查点结果](3.0.0-domain-read-checkpoint.md#已取得的结果)。核心目标仍未达到。第二次普通复测在准备阶段断线，没有测量、没有选入夹具库；11 月 4 日重新连接后仅恢复已替换的 APK，原包摘要与正式包均核对一致。首次失败与恢复分别保留。

开场视口变化的反例确认为真实错误：动画仍使用旧 aspect 的终点。已改为重新拟合两端并保留可见时钟，后台间隔不计入开场；普通／极简开场、视口变化、手动中止及源相机对照定点通过。预热其他页面改等开场完成，首个世界回执采用当时实际模式和任务，避免加载期间开始专注仍沿用旧镜头目标。上述集成仍须 Android 页面和真机补验。

新增独立的定时触点测量，不在定时触点前查询无障碍树。坐标在计时前校准，随后 force-stop 并核对无进程；成功显示实际专注操作区／切到统计面板才能证明核心接受了操作。原无障碍可用时间仍保留。公开 API 的 `UiAutomation.injectInputEvent` 会等待窗口和 Surface 动画，见 [Android 文档](https://developer.android.com/reference/android/app/UiAutomation)；shell 路径直接等待输入事件处理，见 [AOSP 实现](https://android.googlesource.com/platform/frameworks/base/+/81f52b053da6/services/core/java/com/android/server/input/InputShellCommand.java)。这只是排除测量干扰的补充，不将 Android 首帧或过早报告当目标通过。

电脑端返验：本轮 205 项领域／存储／计时／表现核心检查和 11 项开场／相机检查通过。`emulator-actual-root-r1` 的两项直接启动默认 `MainActivity`，由真实 `onResume/onStop` 驱动普通／极简 Home 返回，并核对两种复位和普通四页往返。`emulator-opening-editor-r2-explicit-ime-save` 通过 Android InputConnection 在中间保留中文组合文本后明确保存。任务管理原失败保留；后续记录确认键盘出现后视口缩小，首次滚动的目标已移出可见区，脚本改为按当前视口滚动并等位置稳定后只点击一次。`emulator-editor-touch-r2-task-management` 三项通过，`emulator-opening-four-flows-r1` 四种两轮及蓝图库五项通过，受控文件均还原。它们不是 OnePlus 耗时或发布全量结果。

## 定时触点与缓存未命中

OnePlus `feedback9-fast-core-benchmark-r7`（`7ba0f845…`）仍使用相同 16 MB 输入和 verify 编译，无采样计时：

| 条件 | Android 核心 fully drawn | 实际操作证据 |
| --- | --- | --- |
| 普通、有效检查点 | 434 ms | 750 ms 发起一次真实触点，793 ms 返回，随后真实专注操作区出现 |
| 极简、有效检查点 | 448 ms | 650 ms 发起真实横滑，792 ms 返回，845 ms 观察到统计面板 |
| 普通、另一独立冷进程，使用原无障碍观察方法 | 441 ms | 无障碍树到 1,330 ms 才暴露启用按钮，点击至专注区 806 ms |
| 普通，主动排除实验数据的检查点 | 1,165 ms | 首次完整读取仍未达到核心目标 |

前两条已验证进程退出后重新冷启动；坐标在计时前校准，计时期间输入前不查询无障碍树。第三条没有校准启动，确认短绘制时间并非只在校准后的进程出现。原无障碍方法的数字保留，不能据此将约 900 ms 的观测差额说成应用实际不可操作。缓存命中与未命中分开，也不能只凭这些命中样本宣布整个目标完成。

`oneplus-r7-miss-profile-r1` 的 10 ms 线程 CPU 记录取得 5,819 条、0 栈失配。首次完整解码中，蓝图解析、领域校验与完整规范文本写出仍是主要成本；后台每日备份另占约 937 ms 状态线程 CPU，属于后续首次操作竞争，不能加到核心启动墙钟上。轨迹和匹配 R8 映射保留。坐标去重改成按既有最大尺寸分配的位图，远原点、边界和重复坐标的新反例及原领域／存储检查 207 项通过；`r8` 未命中核心绘制 1,129 ms，仍未达标。

接续修改去掉摘要编码中的逐字节 Formatter，按已读取记录估算有界写出容量，并在成功的方块标量校验中延后创建错误路径文字。校验、规范内容、错误路径及 SHA 对照共 210 项已通过；手机收益待下一份冻结构筑返验。原包、受控文件与领域／恢复事实在上述每份实机记录中均已还原。

后续 `r9`—`r12` 的应用 APK 相同（`1bacf9ad…`）。未命中时核心绘制约 1,042–1,082 ms，仍不能宣布整体达标。`r9` 的坐标参数被远端 shell 拆开，未启动测量；原包与数据恢复成功。`r10/r11` 的手机辅助进程没有按预定 900 ms 唤醒，实际到约 1.27–1.29 秒才发送输入，不能作为一秒内的证据。

定时器改由电脑发送，结果观察器在输入后才启动，并禁止它启动目标或发出输入。最初电脑计时器实为 `GetTickCount64`、分辨率 15.625 ms，后续改用单调的 `QueryPerformanceCounter`（100 ns），逐份保存测量脚本、恢复脚本与输入回执摘要。进一步保持一个仅握手、不启动应用的 shell 连接，减少每次新建 ADB 命令的传输开销。旧失败不改写；输入未被接受或超出一秒的记录仍是失败。

世界准备现等核心跨过绘制帧后再启动；独立宿主保持原行为。`emulator-core-first-frame-r1` 的实际 Activity／Home／复位两项和四模式／蓝图库五项通过，受控文件还原。`r13` 未命中绘制先取得 985 ms，但另一次为 1,083 ms，两个预定触点都没有成功开始专注，尚不足以满足目标。去掉规范对象写出和方块属性检查的逐对象临时列表后，原有 210 项检查通过。`r14`（`13d897dc…`）未命中绘制为 1,023 ms，925 ms 发起、961 ms 返回的触点没有开始专注；这轮仍失败，原包与数据均恢复。没有运行发布全量或交付新用户包。

## 蓝图写出与每日备份的重复成本

`oneplus-r14-miss-profile-r1` 为独立的 10 ms thread-CPU 采样，原始文件保留在 D 盘；5,063 条记录全部配对。按本轮 R8 mapping 还原，完整读取约 729 ms CPU，其中记录重组约 651 ms；蓝图解析约 223 ms，校验等约 246 ms，规范写出约 173 ms。这些是采样的 CPU 归因，不能当作无采样启动墙钟。页面出现后的每日备份另占状态线程约 827 ms CPU，其中隐藏备份列表的再次读取约 214 ms。

后续改动让领域工厂私下解析蓝图原文，扫描器仅对确定的规范拼写给出复用证明，全部语义和关联校验仍执行；规范化改动会撤销复用。最终只省去不必要的蓝图再次写出。恢复清单复用已核验的物理连接印记，任何写入／重连／模式／回滚变化仍检查实际块和引用；未打开的清单不因每日合并而刷新。`canonical-blueprint-parts-r1` 的 216 项、`blueprint-parts-and-backup-stamps-r1` 的 219 项检查均通过，含非规范拼写回退、三种蓝图规范化、共享大蓝图、严格装饰尺寸、同 revision 损坏及外部连接／回滚失效。Android 及无采样 OnePlus 收益待新冻结构筑验证，不先认定达标。

`emulator-blueprint-parts-r1` 的四模式／蓝图库 5 项、16 MB 真实备份与 17 MB 合法长历史往返 2 项、备份损坏隔离 1 项、连接／大文本／Home 恢复 7 项通过。独立检查点的首次写入通过，但读取阶段在损坏缓存后回退 SQLite 时耗尽 192 MiB 堆，整组未通过；实验密钥、缓存、独立数据库及 14 份受控文件均已清理／恢复，模拟器停止。保留原失败，不能把这些分组拼成整组通过。

该容量问题已定位到写出估算：空数组未计字段分隔符。本轮实际规范内容经摘要核对相符，共 16,150,911 个 UTF-16 单元，估算为 16,150,908，少 3 个字符；尾部扩容申请了 64,603,648 字节的新数组。在修正分隔符计数外，大文档初始容量向 4 Ki 字符对齐，最多只多分配一页，小 JSON 不扩大。后续仅返验受影响的容量和检查点场景；`r15` 未进行 OnePlus 性能测量。

用户随后暂停目标。容量估算修正后的 219 项核心检查与两份构筑已完成：`feedback9-blueprint-parts-diagnostic10-r2`、`feedback9-fast-core-benchmark-r16`。模拟器 `emulator-blueprint-parts-r2` 在容量分组执行期间按暂停要求停止；该轮未完成，不能算通过。11 份受控文件恢复核对通过，模拟器已关闭，检查点分组及 R16 OnePlus 计时未开始。恢复工作时先检查这轮容量日志与受影响的检查点回退，再执行已准备的 `run-core-phone-batch.py`；一秒内实际可操作的整体目标仍未验收，P3 未完成。

## 恢复工作：切页、动画与蓝图渲染数据

用户已确认继续这三项。复查暂停前的完整容量日志发现，第一项长历史恢复已经在 480 秒处超时，位置为 `SnapshotStore.prune` 中逐块查询；随后第二项被停止。不能仅归因为用户中断。现将单个恢复根的小块按实际访问顺序每 64 个批读，SQL 以实际文本长度 32 KiB 限制预读，最多保留一批未用内容；大块仍按原标量路径读取。每块的摘要、字节数、链接和完整领域检查不变。221 项核心检查通过。

### 完整世界仍待优化

2026-11-11 用户指出上述 4.4–5.8 秒慢于 v2.9.0 命中缓存后的整体加载。这轮证明的是核心入口提前可用，没有证明完整世界已经跑赢 TS。迁移规划中的完整世界性能门槛仍未验收。

两份样本在世界尚未出现时先开始了专注，分别含普通转沉浸和极简实际选时／双击。它们不是没有中途操作的完整世界冷启动对照。计时工具保留了领域／蓝图校验索引命中情况，但这两个索引不等于地形、景观、建筑几何和最终渲染包全命中。该批结果只提取 `world-facts-reused`／`world-presented`，没有保留可将各段占比分清的完整世界阶段日志，不能补猜本次是否全部命中或哪项独占了几秒。

代码中已确认缓存覆盖不齐：TS 的 `building-cpu-cache.ts` 保存可恢复的几何属性、索引、原创批次、实例矩阵及静态表面；`world-scene-cache.ts` 接入磁盘持久化。原生 `NativeWorldSession` 目前接入蓝图快照、地形和景观文件缓存，但 `OriginalStructureCache`、`BuildingRecipeCache` 及 `NativeWorldPacketCompiler` 的 root／owner 结果主要是进程内复用。冷进程仍需经过建筑施工输入、结构编译、景观与实例打包，以及后续渲染资源采用。两端都需要重建 GPU 资源，不能把 GPU 上传本身说成原生独有的额外开销。

本批首次读库只占 114／201 ms。主瓶颈已转移到工作台可用之后的世界链路；上述缓存缺口是已确认的重复工作来源，但其在 R50 中的具体墙钟占比仍待采样。接续应先按同数据、画质、缓存状态和无中途操作补完整链路分项，再按收益完善跨进程渲染产物复用。不能用渐进显示替代完整世界性能关卡。

### 建筑结构持久化补充

2026-11-15 已为 `OriginalStructureCache` 增加跨进程文件存储；上段“仅进程内”描述保留为此前审计时的状态。几何编码保留组件表面、实例、材质路由及局部原点，带格式版本、输入键、正文 SHA 和严格长度／数值检查。文件损坏时重新生成并修复缓存，不接触领域记录。Android 单独后台写入，文件预算 64 MiB／96 份，内存中待写预算 24 MiB，不将该缓存上传云端。

| 第一组墙钟 | 7.481 秒 | 15.715 秒 |
| 第二组墙钟 | 6.428 秒 | 11.736 秒 |
