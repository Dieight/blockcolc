# 原生后台计时与通知实验

日期：2026-10-19。承接[计时规则](2.9.0-native-focus-port.md)与[只读备份](2.9.0-native-backup.md)。使用隔离包和合成任务，不操作正式 App、数据库、私有同步或全局电源策略。

后续已捕获 `oplus startup` 的系统跳过记录，并完成同包自启动开关对照，见[冷唤起与启动权限](2.9.0-native-startup-policy.md)。以下保留本轮原结果；旧失败与未通过的矩阵报告不改成通过。

## 审计与本轮范围

正式版本的原生服务投影已授权时间线、更新通知，领域会话仍由 Web 恢复后写入。这轮不是再加一个通知时钟，而是让已移植的原生执行器在 Activity 不运行时保存完成事实，并验证它与恢复、替换和手动操作共存。

新入口 `.NativeBackgroundActivity` 只运行最长四分钟的合成计划。它与只读备份实验共用存档结构，但使用独立文件 `native-background-live.json`；不会把原生局部校验器用于真实备份。界面只有显示时钟，不负责推进轮次。前台、后台回调、到点闹钟和重新打开都经过同一条 IO 队列及原子仓库。

仍未移植完整领域、时区业务、专注完整性、奖励和生产世界。没有验收 25 分钟以上的真实计划、深度 Doze、省电模式、重启手机或其他厂商。标准通知数据通过不等于 OnePlus 流体云或 OriginOS 的视觉验收。

## 保存与交接

- 每个事件带替换代次、计划 ID、阶段、会话 ID、绝对截止点和 attempt。仓库在同一个锁内重读最新状态并比对，才允许执行领域转换。重复事件没有新记录，旧阶段／旧会话／旧替换代次不能作用于后来的一轮。
- 自然结束按持久化截止点完成，再按已授权的时间线补齐休息和后续轮次；延迟回调不改变实际专注时长。手动提前或中断则撤销自动推进，确认后才使用新会话 ID 开下一轮。
- 导入只读备份使运行计划消失；回滚提高替换代次并撤销旧计划的自动授权。保存失败时，事实、代次和回滚点都保持旧值，不先发成功通知。
- 保存成功后才更新系统呈现、下一次闹钟和界面快照。损坏文件报错并保留，不重置成首次启动。隔离实验显式清理会留下前一份回滚点，不清应用数据。

## Android 侧

使用计时相关的 `systemExempted` 前台服务，先检查精确闹钟能力。前台服务不运行世界、音频或位置，也不持有长时间 wake lock。常驻进程只等阶段截止点，最多每 60 秒重查壁钟，不用逐秒后台循环。

每个截止点设置普通 exact 闹钟和 allow-idle 备份；同一个事件收到两次仍由仓库去重。allow-idle 的配额和厂商限制没有消失，不能承诺始终准时。不具备 exact 能力时保留 inexact／恢复路径，界面显示受限，不启动不合资格的服务。

服务自身的持续通知不放倒计时。另一个有限时长的阶段通知使用系统 chronometer，按阶段交替 ID，独立设置到期移除；进入等待／汇报时停止 chronometer。这样服务或系统回调迟到，也不需要让过期倒计时无限累加。通知只读已保存事实，不创建会话。

诊断只通过本应用的 `getActiveNotifications()` 读取隔离通知，不采集其他应用正文。每次阶段保存和短延迟通知检查记录时间、PID、代次、阶段与标志；日志有大小上限，不封装进正式 App。

## 验证过程

- 第一次手机执行在授权前被 ColorOS 拒绝 ADB `grantRuntimePermission`，未进入测试：[记录](../../artifacts/experiments/v2.9.0/native-background-device-first/failure.json)。后续改为正常系统通知页面，只核对并操作标题为 `blockcolc · native UI lab` 的总开关，不改 USB 安全或其他应用权限。
- 下一轮 21 项中 20 项通过，一项在磁盘已变为 READY、Compose 尚未收到快照时查找下一轮按钮。补上“同一已保存版本已显示”的前置检查，不改变轮次规则或延长原有超时。[原输出](../../artifacts/experiments/v2.9.0/native-background-device-ui-permission/device-tests.log)。

- 最终 23 项 JVM、21 项 Android 定点通过，[设备结果](../../artifacts/experiments/v2.9.0/native-background-device-final/result.json)与[原输出](../../artifacts/experiments/v2.9.0/native-background-device-final/device-tests.log)保留。关闭 Activity、通知提前完成、零休息手动确认、旧事件、导入／回滚、保存失败与受限分支均有反例。定点不等于手机回到桌面后的调度通过。
- 第一轮独立 Home 测量停在第二轮。发现电脑和手机时钟约差 20 秒，脚本改为按手机时间等待，不改系统时钟；原轮等待得更久，并非提早读状态。[原失败](../../artifacts/experiments/v2.9.0/native-background-matrix-first/failure.json)保留。
- 按手机时间复核，27 秒后磁盘仍停在第二轮；服务状态显示仍是前台服务。随后读取服务客户端诊断时，执行器才追赶到三轮汇报：[保存时状态](../../artifacts/experiments/v2.9.0/native-background-matrix-device-clock/home-state.json)、[阶段记录](../../artifacts/experiments/v2.9.0/native-background-matrix-device-clock/home-events.jsonl)与[服务状态](../../artifacts/experiments/v2.9.0/native-background-matrix-device-clock/home-services.txt)。这支持后台调度受限的判断，尚未据此定位到 ColorOS 内部的具体冻结模块。后续先保存状态／日志，再做可能唤醒进程的客户端诊断，避免把诊断触发的追赶当成准时执行。
- 后台策略对照只操作隔离样机的系统应用详情。ColorOS 可能直接恢复此前的耗电子页，第一次工具检查因此停止、未碰任何开关；[记录](../../artifacts/experiments/v2.9.0/native-background-matrix-unrestricted/failure.json)保留。工具随后同时识别详情页和本应用耗电子页，仍核对完整应用标题。
- 正常界面还有本应用的二次确认，工具起初未识别而停下，随后先取消待确认操作，再补上严格匹配标题的允许／取消分支。只读、允许、恢复三步均单独核对。放宽策略后的首次 Home 三轮通过，后一个场景因 `am start` 复用顶层 Activity、没有执行新的 onCreate 而超时；[原始启动输出](../../artifacts/experiments/v2.9.0/native-background-matrix-unrestricted-final/process-kill-launch.txt)保留。改为每个独立场景先终止隔离包，再创建新计划；没有改应用规则或放宽超时。

## 独立实机结果

OnePlus PJX110、Android 16、USB 连接；每轮 6 秒、休息 3 秒、共三轮。以下除“默认策略”反例外，均临时为隔离样机选择“完全允许后台行为”。没有改正式方块钟的策略。

| 场景 | 结果 | 观测 |
| --- | --- | --- |
| Home | 通过 | Activity 不运行，独立完成三轮；五次阶段交接最大迟到 25ms |
| SIGKILL 终止进程 | **未通过** | 28 秒后仍为第一轮、历史 0；未见自动唤起 |
| 零休息且手动提前 | 通过 | 等待超过原轮截止点仍是 READY、只一条记录；确认后开下一轮，前一轮不丢 |
| 关闭自动续轮 | 通过 | 一轮完成后等待，未擅自开始第二轮 |
| 系统 force-stop | 恢复路径通过 | 停止期间没有执行；重开后按原授权绝对时间补齐三轮，再次打开不重复。不算后台准时完成 |
| 拒绝通知权限 | 事实交接通过 | 确认通知权限为关闭，三轮照常保存；最大迟到 29ms。不声称通知栏可见 |
| 息屏 | 通过 | 唤醒、打开 Activity 和服务诊断之前已保存三轮；最大迟到 26ms |

七个场景观察完成，六项通过，不是“后台矩阵全过”。默认“智能优化”下的 Home 反例仍有效。全部阶段使用原截止点，三个完整自动场景的记录均为 6,000ms × 3，没有把回调延迟计作专注。

三组准时数据的触发源均为 `service-deadline`，证明进程存活时的原生服务交接，不替闹钟冷唤起背书。旧阶段／代次检查包含实际通知 PendingIntent 和执行器入口的注入反例，未模拟系统在导入之后交付一个旧闹钟的全部队列时序。

[汇总与源文件摘要](../../artifacts/experiments/v2.9.0/native-background-summary-final/report.json)重新核对原始状态、事件、通知和 APK；其中 `physicalMatrixPassed=false`。同一应用输入的定点结果不与物理后台失败相互覆盖。修正脚本后只补未覆盖场景和进程终止诊断，没有重跑世界基线或发布全量。

### 进程终止：还不能下根因结论

[独立诊断](../../artifacts/experiments/v2.9.0/native-background-process-death-diagnostic/failure.json)确认终止前已有两个当前 RTC_WAKEUP 闹钟，exact 权限开启；SIGKILL 后 28 秒没有保存下一阶段。系统退出记录为 `SIGNALED / 9`，前后的包状态都是 `stopped=false`，不能拿 force-stop 的正常限制解释这个结果。最终闹钟快照没有这两个待执行项，但仅凭快照不能判定是被清除、拦截还是交付失败。

对应原始资料：[闹钟之前](../../artifacts/experiments/v2.9.0/native-background-process-death-diagnostic/process-kill-alarms-before.txt)、[闹钟之后](../../artifacts/experiments/v2.9.0/native-background-process-death-diagnostic/process-kill-alarms-after.txt)、[包状态](../../artifacts/experiments/v2.9.0/native-background-process-death-diagnostic/process-kill-package-after.txt)、[退出原因](../../artifacts/experiments/v2.9.0/native-background-process-death-diagnostic/process-kill-exit-info.txt)。闹钟输出只保留本包匹配行，不导出其他应用通知。还需补 AlarmManager／广播交付链和 AOSP 对照；目前不能把失败一概归因于 ColorOS，也不能承诺迁移后被杀仍自动运行。

### 通知与恢复收尾

本包的通知快照未出现过期倒计时标记；实际 countdown 的 `when` 与已保存阶段 deadline 一致，并设置到期移除。汇报阶段关闭 chronometer。采样只覆盖若干阶段时刻与配置，不代替连续录屏、OEM 流体云外观或任意冻结时长的验收。

息屏场景结束后安全锁阻挡了设置恢复，脚本因此错误退出，不能记成正常完成；五个场景的原始测量已写出，随后独立校验通过。用户手动解锁后恢复通知关闭和“智能优化”，再次回读确认没有活动计划：[中断补记](../../artifacts/experiments/v2.9.0/native-background-matrix-remaining/runner-interruption.md)、[恢复回读](../../artifacts/experiments/v2.9.0/native-background-matrix-remaining/manual-restoration-readback.json)。原重定向日志为空，未冒充原始控制台日志；后续工具即使恢复被挡也会写明待恢复状态。

隔离包为 `0.6-native-background / 6`，[归档 APK](../../artifacts/experiments/v2.9.0/native-background-device-final/blockcolc-native-background-lab.apk) SHA-256 为 `986ab49bd8d7fc60e0aacf46c1abbf3d7b5b93dacef827a8fe210f2fd8ba0fbd`。定点前后安装摘要与最终回读一致；约 500MB 仍主要是旧冻结世界输入，不是原生发布体积方案。

实验进程已停止，临时通知和单应用后台策略均恢复。通知开关恢复原开／关值，不声称还原 Android 的 `USER_SET` 历史位。正式应用的通知、后台策略、数据和 /100 私人包不变；未构建正式包、跑发布全量、上传或发布。

## 后续

本轮仍是隔离验证，不批准正式存储切换。先定位 SIGKILL 后未自动交付的问题，并保留默认策略的失败；再补长时间／深度空闲、完整语义校验和故障恢复。世界动态、真实备份写回和整套冷启动收益仍未覆盖，不能据此直接开始整套重写。

此处的冷唤起定位已由[后续对照](2.9.0-native-startup-policy.md)接续；默认未授权的失败仍有效。

## 上游依据

- [Android 闹钟调度](https://developer.android.com/develop/background-work/services/alarms)：精确能力、进程外 PendingIntent、取消与空闲限制。
- [前台服务类型](https://developer.android.com/develop/background-work/services/fgs/service-types#system-exempted)：持有相应闹钟权限的适用条件；不代表已获得任何商店发布批准。
- [通知权限](https://developer.android.com/develop/ui/compose/notifications/notification-permission)：通知拒绝与前台服务不是同一个开关；系统任务管理器的呈现也不等于通知栏可见。
- [PendingIntent](https://developer.android.com/reference/android/app/PendingIntent)：令牌可跨创建进程的死亡存活；这不等于已经证明本机闹钟实际交付，不能用文档描述替代上述失败观测。
