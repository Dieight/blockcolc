# 从分项实验转向原生纵向切片

日期：2026-10-19。关联：[上一轮](2.9.0-native-followup.md)。范围是隔离原型；不是将正式 App 整体迁移的决定。

## 为什么换做法

上一轮已经发现局部内核提速不代表完整加载提速，普通 glTF 节点共享也不等于实例绘制。继续让计算、渲染和截图界面各自变复杂，难以回答实际使用是否更好。用户提出先迁整套 App 再测；更合适的中间步骤，是先迁一条真正接通的流程。

本轮把原生界面与真实渲染接起来，先验证世界加载时界面能否可用、活动背景上的玻璃如何取得画面、计时到汇报是否连续，以及 Activity 重建后数据能否接续。它通过后，下一阶段应当是逐段可运行的原生预览版，不再无限扩展互不相连的样机。完整数据／后台业务和画面还没有通过，不能将本轮当作全量迁移收益证明。

## 接通了什么

代码在 [native-ui](../../spikes/native-ui/README.md)，继续使用原有隔离包名，正式 `com.blockcolc.app` 不安装、不关闭、不改数据。

- `LiveWorld` 独立线程拥有 Filament 引擎、资产和帧调度，主线程运行 Compose。输入沿用上一轮同摘要的海岛／海岸 25 栋展开几何、原创纹理、透明材质和阴影；不是重新生成地形的测量。
- 普通／极简布局可双向返回，能拖动相机、切主题和面板浓度。面板取景来自当前 Surface，不再复制旧世界截图；只有面板区域、320 像素宽，异步取景后用原生图层模糊。取景频率和结果逐次记录。
- 用独立合成计划走开始、休息、自动续轮、汇报、保存收据和恢复。计划／收据在一个原子文件里保存；重复汇报不增加记录，读坏文件会显示错误，不按首次启动覆盖它。保留零休息、手动提前结束不自动续轮等反例。
- 原先的截图输入样机与两项测试仍保留，不拿旧截图结果替代本次活动世界。

这不是正式领域代码的完整 Kotlin 移植。短时计划只用来检查状态、线程、界面和保存如何相连；真实任务推进、历史迁移、后台服务／流体云、私有同步、资源包切换和生成增量更新尚未接入。动物 AI、真实天气／天象、水反射及 Three 自定义着色器也未迁入，仍不能认定视觉等价。新样机使用系统字形与简化控件，不是新 UI 提案。

## 测法与边界

同机、同后端、同冻结几何，在关闭取景、10Hz、20Hz 之间轮换。每轮独立启动实验进程；首个引擎提交后三秒预热，然后十秒一圈，同时完成两轮 3 秒专注、中间 1 秒休息、一次主题切换和一次汇报。两种场景各三轮，不与前一轮尺寸不同的 720×960 纯世界直接拼表。

本轮绘制宽 720，纵向尺寸随当前布局的真实纵横比设置。呈现计时依旧读准确 Surface 的 fence；原生 UI 回调、状态提交至 draw 与复制回调各自记录，不把其中任何一个当作 GPU 时间。界面自己不需要每帧变化时，窗口呈现数量也不应直接解释成卡顿。

首个 Compose draw 表示界面已提交绘制内容，世界首个提交也不是实际显示首帧。冻结 GLB 的映射、贴图准备和 GPU 上传包含在原生准备中，但没有生产地形生成、真实数据库或 WebView 启动；文件缓存也未清除。即使数字较小，也不能按它推导 App 冷启动倍数。携带两个大对照 GLB 的约 500MB debug 包只留本地。

复制面板会产生额外传输和位图分配，不能因为能显示就认定这是最终玻璃实现。首个可复制缓冲前可能返回 `ERROR_SOURCE_NO_DATA`，此时显示底色并保留错误码；预热与正式旋转窗口分开，不删除失败请求，也不放宽窗口内失败检查。

## OnePlus 结果

主对照已自然退出，18 份完成报告、零失焦；每份都核对输入摘要、完整六态序列和只新增一份汇报收据。三轮中位数如下，均为 GLES、720×1584；不是上一轮 720×960 的后端排名延长线。

| 场景 | 面板取景 | 世界呈现（次/秒） | 复制返回 P95 | 结束后进程 PSS |
| --- | --- | ---: | ---: | ---: |
| 海岛 25 栋 | 关闭 | 40.4 | — | 361 MiB |
| 海岛 25 栋 | 10Hz | 41.2 | 32.1ms | 391 MiB |
| 海岛 25 栋 | 20Hz | 40.8 | 33.8ms | 420 MiB |
| 海岸 25 栋 | 关闭 | 37.1 | — | 504 MiB |
| 海岸 25 栋 | 10Hz | 38.4 | 35.2ms | 537 MiB |
| 海岸 25 栋 | 20Hz | 39.6 | 38.6ms | 566 MiB |

这组样本没有显示取景导致明确的呈现退化，也不能从海岸数字上升反推“复制越多越快”。开始电池温度 30.9—33.1°C、充电状态；频率顺序反转，仍不是同温度锁频或功耗实验。主要结论是活动取景、计时和绘制能同时工作，而不是整体原生性能胜过现有 App。

首个 UI draw 的组中位数约 184—200ms，世界首次引擎提交约 416—587ms；说明本样机可以在资源准备完成前显示可交互的原生页面。它们有不同边界，世界提交也不是显示首帧，更不能称作正式 App 冷启动降到了半秒。状态提交至 UI draw 的最大记录约 64ms，**不含保存前的操作／文件写入耗时**，不作为触摸到屏幕反馈的完整延迟。

十秒旋转窗口里，10Hz 实际完成 97—98 次复制，20Hz 为 190—192 次；窗口内零失败，首个缓冲前 3—8 次无数据返回单列保存。副本总分配量包含预热，约 46／88—90 MiB；这不是同时常驻内存，却意味着持续分配／回收压力。PSS 同时增加约 30—62 MiB。只采了短窗口，未证明长时稳定、无泄漏或低端设备可接受；最终玻璃应继续评估 GPU 共享／合成路线或自适应取景，不能按这版 CPU 位图路径直接全量迁入。

## 迁移顺序的建议

后续已完成正式计时规则的第一组 Kotlin 对照及无位图玻璃试验，见[局部移植记录](2.9.0-native-focus-port.md)。下面保留本轮切片的取舍，表格不混入后续包的数据。

先形成能真实使用的原生预览版，比先搬完整套代码再首次验收更合适；也比一直增加隔离微基准更接近用户的问题。按以下三个阶段收敛，每段都能运行和检查：

1. 活动世界＋原生页面＋玻璃＋一条持久化计时流程。当前切片用来排查组合风险，不承诺正式画面已完成。
2. 选定渲染和界面路线后，把正式领域规则、备份读取和历史记录逐组迁入，以现有 TS 用例／固定数据作等价反例；同时做后台计时、通知、权限和进程恢复。先用复制的合成／脱敏数据，不让试验格式覆盖正式数据。
3. 原生预览版能走完整日常流程后，才做真正与当前正式版同数据、同画质的冷启、稳态、内存和长时间比较，再处理剩余页面及切换交付。不把 TS 业务、Three 着色器看作可以直接编译为 Kotlin／Filament，也不按实验代码行数估算总工期。

计算热路径是否需要 C++／Rust，仍按在完整流程里的占比决定。当前只得到部分候选结论，整体重写不是既定采用项。
